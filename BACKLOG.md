## Daemon

- A1. Network access, follow-ups. HTTPS and device pairing are done (`daemon/auth.py`, `daemon/https.py`); left:
  - Passkeys as a faster sign-in for paired devices.
  - Bearer tokens for non-browser clients on other hosts (the terminal app over the network). The daemon already accepts `Authorization: Bearer`; no client sends one yet.
- A2. Spending limits on the token ledger (`core/usage`): per job run, per job per day, per conversation and overall per day. Checked before every model call; going over ends the run cleanly (a job run is recorded as over budget, a chat gets a clear message), and a warning at a threshold (80%) goes to Telegram or Slack.
- A21. A LaunchDaemon installed before the logs moved still sends the daemon's output to `~/.lo9i/daemon.log`; the daemon moves it to `output.log` at start (`daemon/launchd.py::move_legacy_output`), but whatever it printed before that (an import error) stays in the old file, which the Logs page doesn't show. The Startup card (both apps) could say the LaunchDaemon is out of date and offer to install it again (one password dialog). The same goes for a LaunchDaemon installed before the daemon could be stopped from the app: its `KeepAlive` restarts it whatever its exit, so Stop is refused until start at boot is turned off and on (`daemon/launchd.py::Service`); the Host card offers Stop and only says so when it's pressed.
- A22. The journal reader (`core/logs/journal.py`) is tested only against a fake `journalctl`. Check on the Linux host that `journalctl --user-unit lo9i-assistant` run as the daemon's user reads the service's output and systemd's notes about it, whatever the journal's storage there.
- A23. Telegram and Slack show only the runs their chat starts: a run the daemon starts in their conversation, like a coding task handed to its agent from a conversation or a follow-up on background work that failed (`daemon/queued.py`), shows in the apps but not in the chat, which hears only the end notice. Show runs started elsewhere in a channel's conversation the way the apps mirror them.
- A32. An update (`daemon/updates.py`) changes lo9i's files while the old daemon still runs: from its `git merge` to the restart, which waits for the runs in progress, modules the daemon imports late and the rebuilt web app served from `daemon/webui` are the new ones, so a tab that reloads then gets the new web app against the old daemon. Build and sync into a staging copy and switch to it at the restart, or restart into the update before anything is served from it.
- A33. On macOS a daemon started by hand while start at boot is on can't be stopped from the apps (`launchd.Beside` refuses): launchd keeps trying to start the LaunchDaemon, and stopping its tries needs an administrator. Ask for the password, as turning start at boot on does, and stop them.
- A38. A doctor that checks the daemon's health once a day, so problems show without anyone reading logs. It reads the day's records in `errors.log` and `daemon.log` (`core/logs/`) and groups them by cause (the last exception line and the last frame in lo9i's code), with how often each happened and when first and last; it reads the conversations' checkpoints for runs that failed and tool calls left without results; and it says what changed since the day before (new causes, causes gone). The result goes to the notifications feed (`core/notifications.py`), with an alert for a cause that's new or growing. Runs as a scheduled job on the daemon's own clock, like Home's daily refresh (`core/home/schedule.py`), and on demand from the apps. Recurring noise that isn't a problem (a channel's network retries) can be marked as known so it stops showing. It also checks that the context a conversation starts with (system prompt, profile, saved facts, recent conversations, skills and tool definitions) doesn't grow too much: it measures it against the model's window and alerts when it passes 30%, saying which parts grew most since the day before.
- A39. A run handed to a coding agent and cancelled twice (the reader gone, then the run cancelled) still writes what the user sent to history, but after the run has ended (`core/agent/handoffs.py`, shielded), so the write can overlap the checkpoint pruning at the run's end (`core/agent/runs.py`). Make the run's end wait for that write.
- A40. A step taken off the queue at the moment a run handed to a coding agent is stopped can be missing from history (`core/agent/handoffs.py::_steps_while`). Collect the steps from the queue and the step in flight before writing the stopped turn.
- A41. While the restart an update asked for waits (`Shutdown.restart_for_update`, `daemon/shutdown.py`), the apps still offer Cancel, which the daemon refuses with 409, and while it waits only for the update they say it restarts now. Add what the pending ending waits for, and whether it can be taken back, to `PendingEnding` and show it in the Host card (web) and `/host` (terminal). The `DELETE /system/ending` docstring in `daemon/api.py` doesn't say it refuses an update's restart either.
- A42. An update in progress whose task is cancelled outright (the daemon's `serve` crashing) kills its step but doesn't go back (`daemon/updates.py`), so the next start may run new commits with old dependencies. Go back at the next start when the last update didn't finish.
- A43. Terminal app: only the prompts and Plugins screens say which events reload them (`RELOADS_ON`); every other screen reloads on each event it's wired to, now in the background. An open Plugins screen isn't reloaded on the `skills` event. And a plugin install dialog (`offer_plugin`) answered in another app stays open, unlike approvals and questions (`tui/app.py`).

## Context

- H1. Better epoch summaries: quote user messages verbatim, keep ids and paths exactly, and let `search_memory` search tool outputs too (it covers only what the user and the assistant wrote).
- H2. How long a provider's prompt cache lasts is known only for some (`core/llm/providers.py`): Anthropic's 5-minute cache, OpenAI's own API (extended retention, about 30 minutes), DeepSeek (hours). The rest use 5 minutes: Gemini's implicit cache and xAI don't document theirs, Groq caches only its gpt-oss models (2 hours), and a provider with no cache could trim at every user message. Anthropic's 1-hour cache (writes cost 2x the input price instead of 1.25x) isn't offered: a choice in Settings → Model could turn it on, with the lifetime following.
- H3. The core tools' definitions are about 6k tokens of every request (26 tools, ~13.6k characters; the largest `schedule_job`, `save_skill`, `search_email`, `update_profile`, `move_to_conversation`, `delegate`). Load groups of them on demand like plugins' tools (`core/plugin_loading.py`): email (`search_email`, `read_email`, `send_email`, `set_up_email`, ~2.4k characters), jobs (`schedule_job`, `update_job`, `list_jobs`, `delete_job`, ~2.5k) and skill writing (`save_skill`, `delete_skill`, ~1.2k), named in the Plugin tools list and loaded with `load_tools`: about 2.5–3k tokens saved per conversation, for an extra step the first time one is used. Then shorten the longest descriptions, moving their guidance into skills where the model reads it only when needed (another 0.5–1k).

## Voice

- A3. Real-time voice agent: live spoken conversation from the browser.
  - A speech-to-speech model (OpenAI GPT-Live) listens and speaks. No separate speech-to-text or text-to-speech step; transcripts come from the model's own events.
  - Audio goes directly between the browser and OpenAI over WebRTC. The daemon only exchanges the connection offer and answer, and never handles audio.
  - The daemon keeps a sideband WebSocket to OpenAI for each call. When the voice model needs to act, it calls a tool; the daemon runs it through `AssistantService`, so Claude stays the brain.

  - Needs an OpenAI key in addition to the Anthropic key. Not needed for Telegram voice notes.
- A4. Spoken replies in Slack. Settings → Audio speaks replies in the web chat and as Telegram voice notes; Slack doesn't get them yet (upload the audio with `files.uploadV2`).

## Open questions and risks

- R1. Bash runs on the host as the daemon's user. It can read `~/.lo9i` (including the database with the Telegram token, the email password and MCP servers' keys) and that user's other files. Only dangerous-command approvals stand in the way. With remote access (A1), a stolen paired device can reach this too until it's revoked. A paired device can also add a local MCP server, which runs its command without approval. Options: run the daemon as a dedicated user with little else on the host, and run just the bash tool in a sandbox container.
- R2. MCP servers send text the model reads (tool descriptions and results). Hidden Unicode tag characters are stripped and write tools on untrusted servers need approval, but visible injected instructions still reach the model. A server whose tool list keeps changing starts a new epoch at each message (a prompt cache miss each time). A server also names the conversation its finished background work is told to by sending back the call's `_meta["lo9i/origin"]` (`core/mcp/background.py`), which isn't signed: it can put a note in any conversation whose id it learned from a call.
- R3. The private watchlist server (lo9i-assistant-extras-private) is trusted, so its `download` tool starts a torrent without approval. A magnet in text the agent read (a web page, an email) could start a download the user never asked for. Options: mark `download` as needing approval while the rest of the server stays trusted, or only accept magnets the user sent.
- Langfuse: run the self-hosted stack and set keys.
