# AGENTS.md

Personal AI assistant built on LangGraph. A daemon on the Mac owns all state and runs the agent; clients (the terminal app and the web app, in `clients/`) talk to it over HTTP; chat channels (Telegram, Slack) are plugins whose processes the daemon runs and that talk to it over HTTP too.

## Layout

```
src/assistant/
  core/          graph, storage (SQLite), observability
    llm/         chat models per provider (Anthropic, OpenAI, GitHub Copilot)
    agent/       AssistantService facade + one mixin per concern
    agent_tasks/ coding agents plugins bring: task records, detached workers, the task tools, handoffs' tasks,
                 telling a task's end to the conversation that started it
    conversation/  system prompt, epochs (compaction), digest, transcript, turn header
      prompts/   prompt texts, one .md file per prompt
    memory/      long-term memory in the Store: profile, facts, episodes; search by meaning with a local
                 embedding model (e5.py), whose vectors a background indexer keeps in their own table, so saving
                 a memory never waits on the model
    tools/       self-registering tools
    integrations/  services connected from the app, one package each: email/ (accounts, providers, smtp, imap)
    channels/    chat channels installed as plugins: their processes (processes.py), the hub they connect to
                 (hub.py: stream, chat operations, setup items, tokens), their chats (chat/: runs shown as
                 messages, buttons, what the user sends), the old core settings handed to them (legacy.py)
    accounts.py  connected accounts per kind (email now), one default per kind; secret_store.py keeps their passwords and tokens encrypted
    skills/      reusable instructions as ~/.lo9i/skills/<name>/SKILL.md, with optional files (scripts, references)
    repositories/  installing skills and MCP servers from git repositories: download, copy, install record
    jobs/        scheduled jobs (cron) and their records
    home/        Home, the web app's landing page: sections (the user's instructions), each built by the worker
                 model from its plugins' read-only tools into one format of items, the last results kept in the Store
    mcp/         MCP servers: settings (Store), connections (hub), their tools as LangChain tools,
                 installing them from a repository (server.yaml; code under ~/.lo9i/mcp/<name>, data under
                 ~/.lo9i/data/<name>), their web pages (pages.py),
                 running a plugin's process (process.py)
    speech/      speech to text (faster-whisper) and spoken replies (Kokoro), set in Settings → Audio; voice audio saved under uploads/audio
    logs/        the daemon's own log: the files it writes (rotated), its records read back as entries with the area
                 they come from (components.py), reading the latest and following a file live (writer.py), the
                 process output read alongside (output.py: output.log or the journal), the level it records at (level.py)
    internet/    the agent's internet access: web search (public engines via ddgs, or the Brave API), page fetching
                 and rendering, URL safety, caching
  daemon/        HTTP API (Unix socket, localhost, HTTPS), device auth, run hub (SSE events), task supervisor, channel routes, scheduler, mail watcher, launchd
  client/        connection.py (connect, auto-starts the daemon), sse.py, errors.py (DaemonUnavailableError),
                 live.py (LiveConversation), files.py (attach by path), recorder.py (microphone)
    daemon_client/ DaemonClient: the conversation as mixins; every other area as a group (`client.channels`, `client.email`, ...);
                 reconnect.py (resumable event streams)
  protocol.py    event JSON shared by daemon and clients
clients/         the apps, each a daemon client
  terminal/      the terminal app (Textual), its own package `assistant_terminal` in the uv workspace; `assistant` opens it
  web/           the web app (SvelteKit); `npm run build` writes it into src/assistant/daemon/webui, served at /app/
```

## Architecture rules

- The daemon is the only process that opens storage or runs the agent. Clients never import `core.agent.AssistantService`; they use `DaemonClient` over HTTP. Conversation calls (`session`, `new_thread`, `send`, `resume`, `events`) sit on the client; every other area is a group named after the part of the daemon it changes (`client.channels.press(name, action)`). New routes go in their area's group, or a new group. Screens receive only the group they use.
- Dependencies point one way: clients -> daemon API -> `core.agent` -> graph -> tools. Core never imports from the daemon or clients.
- Chat channels (Telegram, Slack) are plugins from the extras with a `channel:` section in their server.yaml (`core/mcp/install.py`); the protocol is in `docs/channel-plugins.md`. The daemon runs each enabled one's process (`core/channels/processes.py`) with `LO9I_URL`, `LO9I_CHANNEL` and a token issued for that run. The token reaches only `/channels/<name>/...` (`daemon/auth.py`), where the process holds a stream open (`core/channels/hub.py`), sends what the user does (a message, a button pressed, a command) and tells the apps what to show for it as setup items, which the apps draw with no per-channel code. Everything that is the assistant's runs in the daemon (`core/channels/chat/`): which conversation each message goes to, each run shown as chat messages, approval and question buttons and what pressing them does. It reaches the chat as operations (send, edit, typing, voice) down the stream, each confirmed by the process with its result, so a channel plugin needs no code from lo9i. The daemon also tells the channel its commands (`hello`, then `commands` when an agent plugin comes or goes): /new and each agent's, which hands the channel's conversation to it (`/claude <folder>`, `/claude off`). The plugin declares the protocol version it speaks (`channel: protocol:`); the daemon doesn't run one for another version and the apps say to update it. Core keeps no channel-specific code.
- Messages the agent starts itself (`send_message`) go through `service.outbox`: a channel is registered there while its stream is open. The delivery goes down the stream and waits for the channel to confirm it, so the tool reports real success or failure.
- Every daemon request except `/health` must carry the `X-Lo9i-Client` header (CSRF protection for the network ports). The pages port is the exception: browsers load pages there directly, and the `SameSite=Strict` device cookie it requires is what stops other sites. A client that isn't a browser page (the private watchlist's browser extension, whose requests carry none of the browser's cookies) pairs with `/auth/pair/token`, which returns the device token, and sends it as `Authorization: Bearer`; the pages port takes it like the cookie and never passes it to the page.
- Sign-ins with OAuth (email accounts, remote MCP servers) wait in `core/oauth.py::SignIns` under a one-time state. The browser comes back to the web app's `/app/oauth` page, which posts the state and the code to `/oauth/finish` (`core/agent/sign_ins.py` hands it to the email account or MCP server that started it). That route is open without a paired device (the state is the proof), so the terminal app's sign-in works from a browser on the host that was never paired.
- Mail providers are plugins with an `email:` section in their server.yaml, under the extras' `communications/email/` (`core/integrations/email/providers.py`): presets (servers, OAuth kind, help), no process. An account records the plugin it was connected with and is used only while that plugin is installed and on (`core/integrations/email/plugins.py`); removing the plugin with its data deletes its accounts. A `custom` preset has no servers: the extras' custom-email plugin takes the servers the user types, and installing it takes the accounts that belonged to no plugin (connected by hand before it existed). The allowlist is shared by every account: Settings → General → Email, `/email` in the terminal app.
- Email can sign in with OAuth (Google, Microsoft) through the user's own OAuth app (`core/integrations/email/oauth.py`). The refresh token is the account's secret; access tokens are refreshed when an account is loaded.
- A remote MCP server that answers 401 asks to sign in (`core/mcp/oauth.py`): the SDK's `OAuthClientProvider` discovers its authorization server, registers the assistant there and runs the code flow with PKCE (`core/mcp/sign_in.py`). The registered client, tokens, expiry and authorization server metadata are one secret per server, so a new connection refreshes at the right endpoint. A connection never starts a sign-in: without one, or when the refresh is refused, its status is `needs_sign_in` and it waits for the user to sign in from `/mcp`. A refused refresh (a sign-in that was working) is also recorded as `signed_out` in `core/health.py`: a `signed_out` event alerts every client and it is an alert until the user signs in again or dismisses it. The sign-in is dropped when the server is removed or its URL changes.
- Only the Unix socket is trusted (`daemon/auth.py::trusted`). Every network request, on localhost or HTTPS, needs a paired device: a one-time code from a trusted client, then a token in an `httpOnly` cookie. Never trust 127.0.0.1: port forwarding and proxies make remote traffic arrive from there. Tokens and codes are stored only as hashes (`core/devices.py`). The one other credential is a channel plugin's token: issued in memory each time its process starts, it reaches only `/channels/<name>/...` and is revoked when the process stops.
- Clients learn about background changes from `GET /events` (the `EventBus` in `core/bus.py`), never by polling. Store writes publish automatically (`NotifyingStore`); other changes (skills, job results, runs, bot state) publish explicitly.
- Clients keep running when the daemon is unreachable (`DaemonUnavailableError`). In the terminal app, every handler that calls the daemon is decorated with `@reports_daemon_unavailable` (`clients/terminal/src/assistant_terminal/tui/daemon_errors.py`). In the web app, the event stream's state (`EventHub.getConnection`) shows a banner on every page while it's lost (`ConnectionBanner.svelte`), and every `resource` loads again when it opens again, so pages never show an unreachable daemon as their own error.
- Runs outlive the request that started them. Commands are HTTP requests; a run's events stream as Server-Sent Events and can be replayed by event id.
- Never edit or delete past messages in a checkpoint. History is append-only. The one exception is deleting a whole conversation when the user asks (`delete_conversation`): its checkpoints, list entry, search entries and files go, while memory learned from it stays.
- When a run ends, its conversation's older checkpoints are pruned (`core/checkpoints.py`): only the latest of each namespace stays, which holds every message and the pending writes an interrupted run resumes from, so no message is lost. The daemon prunes conversations saved before this once at start.
- Messages use LangChain standard content blocks (`output_version="v1"` in `core/llm/`). Code that reads messages uses standard block types, never provider-native ones.
- Checkpoints never hold file contents. Attachments are saved under `settings.uploads_dir` and messages keep a `non_standard` upload reference; `core/attachments.py::hydrate` loads them for each model call. Tool results can carry files too (images from MCP tools, an email's attachments): their references go in the ToolMessage's `artifact` (`response_format="content_and_artifact"`), which LangChain never sends; `hydrate` adds them to the result, or to a user message after the results for providers that take images only in user messages.
- The system prompt and tool list stay byte-identical within an epoch, so the prompt cache keeps hitting. The system prompt is built when an epoch starts (`core/conversation/epochs.py`) and stored in graph state. Memory changes take effect in the next epoch.
- Old tool results are sent as stubs once the prompt cache has expired (`core/conversation/trim.py`): at a user message more than `PROMPT_CACHE_MINUTES` after the last model call, tool results before the last `TRIM_KEEP_TURNS` user turns are replaced, from then on, by a stub naming the tool. The point is kept in state and only moves forward, so later calls keep hitting the cache. The checkpoint keeps the results whole.
- Prompt texts live in `core/conversation/prompts/`, one `.md` file per prompt, loaded with `prompts.load(name)`. Code doesn't embed prompt text. Tool docstrings and schema field descriptions stay in code.
- The user edits the persona, the operating instructions and the channel hints (`prompts.EDITABLE`) from the web app's Settings → System prompt (`GET /settings/prompts`, `PUT` and `DELETE /settings/prompts/<name>`; `core/conversation/prompt_edits.py`). An edit is a file used instead of the built-in text, read by `prompts.load` each time: the persona's is `SOUL.md`, the others' `~/.lo9i/prompts/<name>.md`; saving the built-in text or resetting deletes it. An edit that can't be read (not UTF-8, no permission) is logged and the built-in text used, and Settings → System prompt shows the problem with Reset, so a broken SOUL.md never stops the assistant. The other prompts aren't editable: they are templates the code fills in or say how a feature works. Each epoch records a digest of the texts its prompt was built with (`prompt_texts` in graph state); when they change (an edit, or an update to a built-in one), the next user message starts a new epoch with nothing summarized, as with a rename. A `prompts` event tells the clients.
- Per-turn context (date, time, channel) goes in the turn header at the start of each user message, never in the system prompt.
- A new epoch starts only at a user-message boundary, so tool calls and their results are never split. The one exception moves nothing: after a round of tool calls with `offer_plugin`, when the user installed a server, the epoch is reopened at the same point with its tools (`graph.py::_installed_node`), so the agent uses them in that run.
- A new epoch waits only for the running summary of the part it archives (`core/conversation/summary.py`). Memory from that part (episode, profile, facts) is digested after the reply: the part is recorded in the Store (`core/conversation/pending.py`) and the memory writer (`core/conversation/memory_writer.py`, a supervised daemon task) digests parts one at a time, at start and as they're added, so none is lost to a restart.
- Renaming the assistant (`core/identity.py`, `/name` or the `rename_assistant` tool) starts a new epoch at the next user message: the system prompt is rebuilt with the new name and nothing is summarized. Channels hear about it on their stream; the Telegram bot's display name follows the name.
- There is no main conversation: each topic has a conversation of its own. A message written outside one goes to the user's inbox (`core/inbox.py`), which routes it without asking: the graph's first node (`core/conversation/dispatch_nodes.py`) has the worker model pick where it goes (`core/conversation/dispatch.py`: the conversations its words match, then the most recent, each with when it was last written in, numbered in `prompts/dispatch.md`; archived ones never). A short message that obviously follows up the one before it (that one sent on to a conversation from the same channel, written in there under `FOLLOW_UP_SECONDS` ago, no words matching another conversation's tags) goes where it went without the model (`core/conversation/follow_up.py`); each pick is logged with where the message before went. It goes on in the conversation it continues, or into a new one, which it also does when the model is less sure than the confidence (Settings → Model, `/model`; `core/conversation/dispatch_setting.py`, 0.7 by default), since a wrong new conversation costs least. A quick question one answer settles is answered right in the inbox; a quick exchange lasts `INBOX_TURNS` of the user's messages, and the next one about it moves to a new conversation with what was said (`core/conversation/carried.py`): a turn header note for the model (`prompts/carried_from_inbox.md`), and the lines kept in that message's `additional_kwargs`, which no model call sends, so the apps show the exchange before it, live (`Dispatched.carried`) and in history (a `carried` shown message); the exchange in progress is kept in graph state (`inbox_exchange`). A message sent on is kept in the Store (`core/conversation/dispatched.py`: its content, files and what a voice note said included, and the notes taken when it was written in the inbox, which go with it) and the inbox records it with a line saying where it went; a `Dispatched` event tells the client that sent it, which goes there once the run ends (the web app opens it beside the others, the terminal app moves to it, a channel runs it there) and sends it by id (`POST /threads/<id>/dispatched/<dispatch id>`, `send_dispatched`), which adds that conversation's turn header notes. Its line in the inbox carries the message's id: the web app's Move on it, or `/move` (the last one) in the web and terminal apps, runs the inbox again (`POST /threads/<inbox>/moves`, `move_dispatched`), which picks among the other conversations, asks (moving is the user's correction), and sends it on by the same id; the conversation it left gets a turn header note to leave it out (`core/conversation/moved.py`), since history stays. The assistant moves work that outgrows a quick answer out of the inbox itself, without asking: `move_to_conversation` (`core/tools/side.py`) keeps a brief like a routed message and sends a `Dispatched` event for a new conversation. Unattended runs and conversations of their own go straight to the epoch and the agent. Each conversation has tags the worker model writes with its title (`core/conversation/titles.py`; names and topics, in the user's language and English; a titling that fails is tried again at the conversation's next reply, and the next one that succeeds titles the others waiting, `core/agent/titles.py`), which routing matches a message against (`core/conversation/related.py`; a tag counts when all its words are in the message, and words few conversations' tags use weigh more). The apps open Chat on the list of conversations, newest activity first (the web app's `/conversations`; the terminal app's start and `/inbox`, with `/conversations` to open one); the inbox is a small entry of its own for quick questions and where each message went. Each client (terminal, browser tab) holds its own conversation: `/new` starts one, `/inbox` goes back to the inbox, `/conversations` opens one. A browser tab holds several side by side (`clients/web/src/lib/chat/openChats.ts`), each under a client id made from the tab's (`partClientId`), so their replies run in parallel: `/new` and the sidebar's + open one beside the others, the sidebar lists them under Chat with any other conversation that has a reply (`GET /runs`) or a coding task running, and closing one tells the daemon (`POST /threads/leave`), which leaves it. A browser tab keeps its open conversations across reloads. A chat channel (Telegram, Slack) has no client to hold one (`core/channels/chat/conversations.py`, `core/agent/channel_threads.py`): a new message goes to the inbox; a reply to a message goes on in that message's conversation, since every message sent in the chat, and the user's own when the plugin sends its id, is kept with its conversation (`core/channels/chat/threads.py`); `/new` sends the next message to a new conversation; and while the conversation the channel last wrote in is handed to a coding agent, messages go on there. Each reply there starts with a short tag of its conversation (`[watchlist] …`: its first tag, or the start of its title; `[inbox]` for a quick answer). Runs are announced with the `client_id` that started them, so every other client on that conversation shows them live.
- The home conversation from before the inbox is kept, once, as an archived conversation (`ThreadsMixin.retire_home`, at daemon start): retitled "Home (before the inbox)", listed and readable, never routed to and never retitled, and what's new in it archived into memory; channels' saved conversations are dropped, so their next message goes to the inbox.
- A conversation no client is on any more is left and archived in the background (`daemon/clients.py`, `core/agent/archive.py`): right away when its client moves to another, after a grace period when its client disconnects. Archiving leaves the part to the memory writer, which adds an episode plus profile and fact updates; covers only what's new since the last archive, and is skipped below `EPISODE_MIN_TURNS`.
- Tools register themselves with `@register("<toolset>")` in a module under `core/tools/`. Enabled toolsets come from settings, never per channel, because a conversation spans channels.
- Every model call is recorded in the token ledger (`core/usage/`: `model_calls` and `token_parts` in SQLite) by a `TokenMeter` set on the model with `llm.metered`, never passed in a call's config (that replaces the run's callbacks and stops streaming). A new place that calls a model attaches a meter with its purpose. The ledger keeps tokens only; `core/usage/prices.py` turns them into money when a report is shown.
- Prefer bash or MCP over a new tool. Every tool definition is sent on every model call.
- New features go in a git repository, not in core: a skill (`<group>/<category>/<name>/SKILL.md`, optional `scripts/`) when it needs only steps or code without secrets, an MCP server (`<group>/<category>/<name>/server.yaml`, format in `core/mcp/install.py`) when it needs secrets, an outside service or a connection that stays open. A chat channel is a plugin with a `channel:` section. Core changes only for the assistant itself (the channel protocol, memory, models, approvals, the apps).
- Only the user installs plugins: installed code runs on this computer. Plugins come from the assistant's extras (`core/repositories/known.py`), built in and the only official repository, and from https repositories the user adds under Repositories in Plugins (web app) or `/plugins` (terminal app), which aren't official (`core/repositories/listed.py`, one Store record). A private one is added with a token that can read it, kept with `core/secret_store.py` and given to git only as an Authorization header for its host, in git's environment (`core/repositories/checkout.py::_auth`); git runs without the system config, so a Mac's Keychain never signs in for it. Plugins lists every repository's plugins, each marked Official or with its repository; a plugin lo9i can't read is left out with its problem (`RepositoryContents.problems`), never the rest of its repository, and `python -m assistant.core.repositories.check <folder>` checks a repository the same way before it's pushed (the extras' pre-commit hook); and installs one from the repository it's listed under; removing a repository leaves what was installed from it, which keeps updating from there; a private one's token stays until the last plugin from it is removed. The update checker reads every listed repository; the agent offers only the extras' plugins. They install from Plugins (web app) or `/plugins` (terminal app), or when the agent offers one: the extras' plugins not installed are listed in the system prompt (`core/repositories/offers.py`, from the listing the update checker keeps), and `offer_plugin` (`core/tools/plugins.py`) pauses the run with a `kind: "plugin"` request that the web and terminal apps show as the install dialog. After an install there, a plugin with a setup (email accounts, a channel's pairing) goes on to it in the same place, and `open_plugin_setup` opens that setup later (`kind: "plugin_setup"`, answered `{"done": true}`). Tokens are typed there and go to the daemon, never through the chat; chat channels can't show it, so there the agent points the user to the app. The tool reads whether the plugin is installed afterwards instead of trusting the answer. Mail providers are the one exception the agent installs itself: their plugins run nothing, so `set_up_email` asks the user which provider their account is with (an `ask_user`-style question), installs that plugin, and opens its accounts (`plugin_setup`); the email tools point to it when no account is connected. When the agent saves or deletes a skill, `approval.ask` asks the user first, so text the agent read can't plant one.
- Every plugin has a category from the fixed list in `core/repositories/categories.py`: a group and a category in it (`communications/email`, `apps/finance`). In the extras a plugin lives in its category's folder (`communications/email/gmail`), which gives its category; a plugin outside those folders declares `category:` in its server.yaml or SKILL.md. A section can require one (a channel is in `communications/chat`, an email provider in `communications/email`). Plugins lists plugins by group; the category only groups them, and what a plugin does comes from its sections. A plugin's own setup (a channel's items, an email plugin's accounts) shows in its details there; group names are only headings, not settings. A plugin that runs only on some systems declares `platforms:` (`linux`, `macos`; `core/repositories/platforms.py`) in its server.yaml or SKILL.md; on any other system it isn't found in the repository, so it's never listed, offered or installed there, and an update that drops this system is refused.
- The user pins skills to a conversation (`/pin`, `/unpin`; `core/conversation/pinned.py`, a Store record per conversation). Their instructions go in full in the system prompt of every epoch, so they last the whole conversation, unlike a `use_skill` result that is trimmed and summarized away. Pinning or unpinning starts a new epoch at the next user message with nothing summarized, as with a rename, and that message's turn header says what changed, once.
- A plugin can use a login of lo9i's instead of one of its own: `model_login: copilot` in its server.yaml gives its MCP server the Copilot model provider's GitHub token as `LO9I_COPILOT_GITHUB_TOKEN` (`core/mcp/logins.py`). The hub adds it when it starts the server, it's never saved with the plugin, and a change in `/model` reconnects the servers that use it. The install dialogs say the plugin uses it. A field marked `optional: true` may be left empty.
- A plugin can bring a coding agent (`agent:` in its server.yaml: command, name, worker; `docs/agent-plugins.md`). The plugin brings only the worker, a command that runs one task; everything else is the daemon's (`core/agent_tasks/`): each task is a folder in the plugin's data folder (task.json, pid, progress.log of JSON steps, result.json), the worker is started detached with the plugin's env, keys and login so it outlives a restart, and the daemon follows its files with watchfiles. While an agent plugin is installed the assistant gets the task tools (`start_task`, `task_status`, `list_tasks`, `stop_task`, `core/agent_tasks/tools.py`); they come with the MCP tools through `core/plugin_tools.py`, frozen per epoch, and starting or stopping a task asks the user unless the plugin is trusted. Where the user watches, a task goes to the agent as a conversation, so its steps are that conversation's, kept in history. In a conversation, `start_task` hands that conversation to the agent and queues the task (`core/conversation/queued.py`), which the daemon sends as a run of its own once the reply ends (`daemon/queued.py`), so every app shows it. In the inbox it moves the task to a new conversation without asking (`moved_out_of_inbox`, `core/tools/side.py`): the task is kept like a routed message with the agent's command and folder, and `send_dispatched` hands the new conversation to the agent before the task goes to it (to the assistant instead when the folder went away). The inbox itself can't be handed over; `/claude` there hands a new conversation. In a scheduled run the task runs in the background. While `task_status` waits for a task, its steps show inside that call (`steps.py::within_call`); while any task runs, every step is an `agent_task_progress` event and `GET /agent-tasks/running` lists the running tasks with the conversation that started each and their latest steps, which the web app shows above the composer and the terminal app under its title (`core/agent/tasks.py`). The apps add its command: `/claude <folder>` hands the conversation over (`core/conversation/handoffs.py`, a Store record per conversation), `/claude` alone opens a folder picker (the workspace `~/.lo9i/claude-workspace`, folders used before, browsing from the home folder; `core/conversation/agent_folders.py`), `/claude off` takes it back. While it's handed over, each message runs as a task continuing the conversation's session in that folder (`AgentTasks.converse`; no model, no approval: switching is the user's consent) as a cancellable run, and the message and reply are appended to the conversation; while it works, what the user writes there goes to the task between its steps (`message_agent`; the task's `inbox/`, `docs/agent-plugins.md`), and the API's `interrupt_agent` stops its step in progress, leaving it waiting for the next message (no app offers it), and those messages show among its steps (`UserSaid`), live and in history; once it is done with the job (its run ends with a reply or an error, and no message waits in the conversation's queue) an `agent_finished` event tells the apps, and the web app plays a sound and shows a pop-up, each turned on or off per browser in Settings → General (`lib/agentDone.ts`); when it comes back, the next message's turn header tells the assistant the replies were the agent's, once. Files sent to an agent are saved and kept in the conversation like any attachment; the agent gets their full paths after the message and reads them from disk (`core/agent/messaging.py::_to_agent`). Its steps become the run's events (`core/agent_tasks/steps.py`): `TextDelta` for what it says and for its thinking, which shows as a message like its reply, and a `ToolStarted`/`ToolFinished` per call, so the work reads like a reply, its words streaming as they're written (`text_delta`, `thinking_delta`); a note goes inside a call named after the agent. The steps are kept with the reply in its message's `response_metadata`, which no model call sends, so history shows them again (`core/conversation/display.py`). A plugin written for the old format (an MCP `converse` tool) isn't offered until it's updated.
- MCP servers are added from the app (`/mcp`), never by the agent. Their tools are named `mcp__<server>__<tool>`; the user picks which ones the agent gets. Each epoch freezes the MCP tool definitions in graph state (`mcp_tools`); when they change, the next user message starts a new epoch with nothing summarized, as with a rename; a server installed from `offer_plugin` brings its tools right after that call instead (the tool waits up to `_START_SECONDS` for it to connect, `McpHub.started`). Calls look the tool up live in `McpHub`, so a tool turned off stops working at once. Local servers run on demand (`core/mcp/on_demand.py`): their tools are kept from their last connection (`core/mcp/tool_cache.py`), the first call starts them and they stop after `IDLE_SECONDS` without calls; an update forgets the tools, so the server starts at once to learn them again. Remote servers stay connected. On an untrusted server, tools not marked read-only go through `approval.ask`; after a dropped connection only read-only calls are retried.
- Failures of MCP servers and skills are counted in a row per server and per skill (`core/health.py`, in the Store): failed connection attempts and failed or erroring MCP calls (`core/mcp/connection.py`), and skill scripts that exit non-zero or time out, found by their folder in a bash command (`core/skills/tracker.py`, a run callback reading bash's exit-code artifact). Only a working call or script clears the count. At `FAILING_AFTER` in a row a `failing` event alerts every client, and it becomes an alert (`core/agent/alerts.py`, the web app's Alerts page and sidebar bell) that stays until the user dismisses it or it works again; a turned-off server or deleted skill has none. The /mcp and /skills screens show the count and the last failure. A skill whose SKILL.md header is invalid or whose instructions use files it doesn't have lists its `problems`; such a skill isn't installed, updated or saved.
- An MCP server installed from a repository can come with a web page (`page:` in its server.yaml). `core/mcp/pages.py` runs it on a Unix socket in the server's data folder; `daemon/pages.py` serves it to paired devices on the daemon's port plus one, a separate origin so its scripts can't call the API, removing the device cookie and refusing its cookies. The web app shows it in an iframe from the sidebar.
- Actions that need approval go through `core/tools/approval.py::ask`: bash commands matching `bash_guard.py`, email to recipients outside the allowlist. In unattended runs (channel `worker`, scheduled jobs) the scheduler forwards them to the channels registered in `service.approvals` (`core/approvals.py`; every connected channel, with `ja:`/`jr:` buttons) and waits up to `JOB_APPROVAL_MINUTES`, which doesn't count toward the run's time limit. With no channel connected, or no answer in time, they are denied and the job is recorded as needing attention. Runs in progress are kept in the Store (`core/jobs/active.py`): after a restart, a run that was waiting for approval asks again once a channel connects, and one stopped anywhere else is recorded as failed.
- The agent asks the user to pick among options with `ask_user` (`core/tools/questions.py`). It pauses the run like an approval: an `ApprovalRequired` whose request has `kind: "question"`, answered with `{"choices": [...]}` (`null` when skipped). Every client shows it: checkboxes in the web app, a selection list in the terminal app, buttons in Telegram and Slack (the picks travel in the button data, `core/channels/chat/questions.py`). Unattended runs aren't asked.
- The agent hands self-contained tasks to a subagent with `delegate` (`core/tools/delegate.py`, `core/subagent.py`): a small graph on the worker model with its own prompt and no epoch, memory or turn header, run inside the tool call, whose final reply is the tool result. It gets only tools registered with `subagents=True` (they read or work on this computer; nothing that talks to the user, sends, schedules or saves) and read-only MCP tools, and its last step's tool calls don't run (`SUBAGENT_MAX_STEPS`). Every tool call runs as a task of its own (`graph.each_tool_call`), so a subagent's checkpoint lives under its call's namespace in the conversation's thread: an approval inside it pauses the run, and the answer resumes it where it stopped. Its tool calls stream as `ToolStarted`/`ToolFinished` with `within` set to the delegate call's id, which the apps show inside that call. Scheduled jobs don't delegate.
- Messages the assistant sends on a channel from outside that channel's conversation (`send_message` from a job or another chat, new-mail alerts) are recorded with `core/conversation/sent.py` and go into the turn header of the user's next message on that channel, once.
- The web app opens on Home (`core/home/`, `GET /home`): sections the user edits (title, what to show, the plugins it reads; `PUT /home/sections`, built-in ones from `prompts/home_<id>.md` until then), each built by the worker model with only the read-only tools of its plugins (`core/home/builder.py`: a small graph gathers, then `build_structured` writes `SectionContent`, items with a day and time, which pydantic validates). Plugins aren't changed for it. Each section's last result is a Store record, saved as it's built (a `home` event), so the page shows the last results at once and updates itself; one that fails keeps its items and says why, one whose plugins aren't installed says so without a model call. Showing Home asks for a refresh (`POST /home/refresh`), which runs in the background unless one runs or the last ended under `FRESH_MINUTES` ago that same day; Refresh forces it, and saving sections builds the new and changed ones. The daemon keeps it current on its own (`core/home/schedule.py`, a supervised task ticking on the wall clock): on the first tick of the user's day, and every `WATCHED_MINUTES` while a client shows it (the web app's Home tab says so while it's visible, `PUT`/`DELETE /home/watch`; a client whose event stream closes is forgotten, `ClientRegistry`'s `gone`).
- Job results and background work that ended go to a notifications feed apart from any conversation (`core/notifications.py`, a Store record each, the latest 200): the scheduler adds each job run's result (`daemon/scheduler.py`; not runs skipped or missed), `BackgroundEnds` each end, named after the conversation it was started in and linking to it. The web app's Notifications page and the terminal app's `/notifications` list them, newest first, open the conversation, dismiss or clear them (`GET /notifications`, `POST /notifications/read`, `DELETE /notifications[/<id>]`); the sidebar counts the unread ones. Toasts and chat channel messages still come as before.
- Background work that ends after its call returned is told to the conversation that started it (`core/background.py`, `docs/background-work.md`): a note in the turn header of the user's next message there (`core/conversation/ended.py`), an entry in the notifications feed, a `background_ended` event every app shows as a toast (the web app's opens the conversation), and a message on the chat channel it was started from, kept with that conversation so replying to it goes on there (as `send_message`'s are: `Outbox.send` returns the ids the channel confirmed, `core/channels/chat/threads.py::record_own`). When the work failed, or its end asks for it (`follow_up` in an MCP server's `work_finished`), the assistant follows up unasked: a follow-up is queued in that conversation (`core/conversation/queued.py`) and the daemon runs it once nothing runs there (`daemon/queued.py`, woken by a `queued_messages` event), a message with only the note and no text of the user's (`core/agent/follow_ups.py`), which routing skips and the apps show as the notice (a `notice` shown message); not in a conversation handed to an agent or waiting for an answer. Tasks started with `start_task` are recorded with their conversation (`core/agent_tasks/reports.py`) and followed to their end by `TaskEnds` (`core/agent_tasks/ends.py`, a supervised daemon task), across restarts; when the assistant reads the end first (`task_status`, `stop_task`) nothing is told, and an end is never told while `task_status` is reading the task. An MCP server reports its own: every call carries `_meta["lo9i/origin"]`, which the server sends back in `notifications/lo9i/work_finished` on its connection (`core/mcp/background.py`, the client extension `lo9i/background`); between `notifications/lo9i/work_started` and the end, a server on demand isn't stopped as idle.
- The mail watcher (`daemon/mail_watcher.py`) keeps one IMAP IDLE connection open while new-mail alerts or a mail job want it, and hands new messages to `Scheduler.run_for_mail`. The last UID seen is saved before delivery, so restarts never repeat or flood.
- Jobs repeat on a cron `schedule`, run once `at` a local time (then turn themselves off), or run `on_new_mail`. Scheduled jobs run in their own conversation (`job:<name>:<time>`), are never archived as episodes, and only run while the daemon runs. `/startup` makes the daemon run from boot: LaunchDaemons on macOS (with Ollama), a systemd user service on Linux (`daemon/startup.py` picks the backend).

## Code rules

- No quick workarounds or shortcuts. Fix the cause with the right design, even when a stopgap (polling, sleeps, retries, special cases, silenced errors) would be faster. If a proper fix isn't possible yet, say so and add it to `BACKLOG.md` instead of shipping the stopgap.
- Private functions, methods and attributes start with `_`. Anything without `_` is public API of its module.
- Keep functions small and single-purpose. If a function needs a comment to separate its steps, split it into functions. Aim for under ~20 lines.
- Apply SOLID:
  - Single responsibility: one reason to change per class and module.
  - Open/closed: add behavior with new classes or functions (new tool, new channel) instead of editing unrelated code.
  - Liskov: subclasses and protocol implementations must be usable wherever the base is expected.
  - Interface segregation: small protocols with only the methods callers need.
  - Dependency inversion: depend on abstractions and pass dependencies in (constructor or arguments). No hidden globals beyond `settings`.
- Large classes are a facade composing mixins, one file per concern (see `core/agent/`). Shared attributes are declared on a base class. New behavior goes in a new or matching mixin, never in the facade.
- Type hints on all public signatures.
- Async all the way in core. No blocking I/O in async code.
- Match the style of surrounding code. Comments explain why, not what.

## Tooling

- Python 3.12, managed with `uv` as a workspace: the root package and `clients/terminal`. Add dependencies with `uv add` (`uv add --package assistant-terminal` for the terminal app), never pip.
- Before every commit run `uv run ruff format`, `uv run ruff check` and `uv run pyright`, and `npm run format` in `clients/web` (Prettier); all must pass. Fix findings instead of disabling rules. A `# pyright: ignore` is only for a verified defect in a library's types, with a comment saying which.
- Tests live in `tests/`, one folder per area (core, internet, daemon, client, terminal); the channel plugins' tests live with them in the extras. Run `uv run pytest` before every commit; it is offline and uses temporary data paths, never `~/.lo9i`. `uv run pytest -m live` runs the tests that need the network or large downloads (search engines, page rendering, the speech model).
- New behavior comes with tests. Use the fixtures in `tests/conftest.py`: `script` (fake model replies), `digests` (fake epoch digests), `service`, and `tests/terminal/conftest.py` for the terminal app.
- Run locally: `scripts/run.sh` (starts Ollama when `.env` points at it, then the terminal app, which starts the daemon). Nothing runs in Docker. `assistant daemon` runs the daemon in the foreground. The daemon writes its log itself, however it was started (`core/logs/`): `~/.lo9i/logs/daemon.log` and `errors.log`, rotated, shown in the web app's Settings → Logs and `/logs`, which follow them live over Server-Sent Events; in a terminal its records show there too. What isn't a record (a crash before logging starts) goes to `~/.lo9i/logs/output.log` when the terminal app or launchd started it, to the journal under systemd; the Logs page shows it as `output` and follows it by watching the file (watchfiles) or with `journalctl --follow` (`core/logs/output.py`). A LaunchDaemon installed before the logs moved still sends it to `~/.lo9i/daemon.log`, so the daemon points its own stdout and stderr at `output.log` at start (`daemon/launchd.py::move_legacy_output`). The level it records at is a setting (Settings → Logs, `/logs`; `core/logs/level.py`) applied without a restart: to the assistant's own loggers, while libraries stay at INFO. A plugin's process (a channel, a page) logs its output under a logger named after it (`assistant.core.channels.<name>`, `assistant.core.mcp.pages.<name>`), so channels are a component of their own. `scripts/restart.sh` (`assistant daemon restart`, POST `/system/restart`, `daemon/shutdown.py`) restarts the running daemon so code changes take effect, once no run is in progress. Restart it that way, never by stopping its process: a conversation handed to an agent (/claude) runs inside the daemon, so stopping it stops that agent before it replies. The apps restart or stop it too (Settings → System, `/host`; POST `/system/stop`), also once no run is in progress. A restart starts the process again in place, however it was started; stopping depends on what started it (`daemon/managers.py`): one started by hand exits, systemd is asked to stop its service, and launchd leaves it stopped after a clean exit (its plist's `KeepAlive` is `SuccessfulExit: false`; a plist from before restarts it whatever its exit, so stopping is refused until start at boot is turned off and on). A daemon that finds another one running exits with `EX_TEMPFAIL`, so the service manager tries again.
- Install: `install.sh` at the repo root, piped from curl (clones into `~/lo9i-assistant`) or run in a checkout. It installs uv and the dependencies, asks for the provider and key the first time and writes `.env` on that computer, and on Linux runs the daemon as the same systemd user service `/startup` installs. `scripts/deploy.sh user@host` copies this working tree to a host and runs install.sh there; it never copies `.env`.
- Data lives in `~/.lo9i`: `lo9i.db` (SQLite), `uploads/`, `models/`, `workspace/` (bash), `browsers/` (headless Chromium for page rendering), `SOUL.md` and `prompts/` (the user's edits of the system prompt texts), `daemon.sock`, `logs/` (the daemon's log), `cli_history` (the terminal app's input history, kept by the client).
- The model (provider, its fields, main and worker model) is set from the app with `/model` or Settings → Model, saved in the Store and overriding `.env` (`core/llm/choice.py`). Providers are listed in `core/llm/providers.py`: Anthropic, Copilot and OpenAI-compatible have their own builders, every other one goes through LangChain's `init_chat_model` with the field values as keyword arguments. A provider's package is installed with uv when it's first chosen, or at start if it went missing (`core/llm/packages.py`); `install.sh` syncs with `--inexact` so deploys keep them. Saving asks each model to answer once; the service then rebuilds its graph, digester and titler (`core/agent/model.py`), so the change applies without a restart. Model builders take a `ModelChoice`, never read the provider from `settings`. The Copilot and OpenAI-compatible models connect with TCP keepalive (`core/llm/connections.py`): a computer that sleeps counts timeouts only while awake, so a call on a connection that died in the sleep would otherwise wait out its 600s read timeout in time awake, hours on a laptop.
- Telegram and Slack are installed as plugins (`/plugins`, or Plugins in the web app), their tokens entered as the plugin's fields; their setup (pairing, status) shows in the plugin's details in Plugins. Telegram's paired accounts live in the plugin's data folder. Slack uses Socket Mode, so it needs no public URL.
- A plugin's keys are encrypted with `core/secret_store.py` (`core/mcp/keys.py`): the values its fields were given, and every env and header value of an MCP server added by hand. Its Store record keeps their names with empty values, so a server is saved with `keys.save`, never `servers.save`, and whatever starts or connects it (the hub, pages, channel processes, updates) fills them in with `keys.fill`. Removing a plugin keeps its keys, and a private repository's token when nothing else needs it, and returns them (`KeptKeys`): the apps ask Keep or Delete (`POST /plugins/keys/forget`). Kept keys fill the fields left empty when it's installed again. A server added by hand has nothing to install again, so its keys go with it. Keys saved in plain records before are moved out when the daemon starts.
- Services the user can connect more than once (email now) are accounts (`core/accounts.py`): a Store record per account with its settings, one default per kind. Their passwords and tokens, and the model's API key set in the app (`core/llm/choice.py`), go only through `core/secret_store.py`, encrypted with the key file at `SECRETS_KEY_PATH` (`~/.lo9i/keys/secrets.key`, outside the database), never in a plain Store record. Tools that act on an account take an `account` argument (label, address or id; empty for the default), and the system prompt lists the accounts at the start of each epoch, so the tool list never changes.
- Web UI conventions, including the default page layout, are in `clients/web/WEB.md`. Follow them for new pages.
- Never require the user to run shell commands for app features. Setup flows go through the daemon API so every client, including the web UI, can offer them.
