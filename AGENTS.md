# AGENTS.md

Personal AI assistant built on LangGraph. A daemon on the Mac owns all state and runs the agent; clients (the terminal app and the web app, in `clients/`) talk to it over HTTP; chat channels (Telegram, Slack) are plugins whose processes the daemon runs and that talk to it over HTTP too.

## Layout

```
src/assistant/
  core/          graph, storage (SQLite), observability
    llm/         chat models per provider (Anthropic, OpenAI, GitHub Copilot)
    agent/       AssistantService facade + one mixin per concern
    agent_tasks/ coding agents plugins bring: task records, detached workers, the task tools, handoffs' tasks,
                 telling a task's end to the conversation that started it
    conversation/  system prompt, epochs (compaction), digest, transcript, turn header
      prompts/   prompt texts, one .md file per prompt
    memory/      long-term memory in the Store: profile, facts, episodes; search by meaning with a local
                 embedding model (e5.py), whose vectors a background indexer keeps in their own table, so saving
                 a memory never waits on the model
    tools/       self-registering tools
    integrations/  services connected from the app, one package each: email/ (accounts, providers, smtp, imap)
    channels/    chat channels installed as plugins: their processes (processes.py), the hub they connect to
                 (hub.py: stream, chat operations, setup items, tokens), their chats (chat/: runs shown as
                 messages, buttons, what the user sends), the old core settings handed to them (legacy.py)
    accounts.py  connected accounts per kind (email now), one default per kind; secret_store.py keeps their passwords and tokens encrypted
    skills/      reusable instructions as ~/.lo9i/skills/<name>/SKILL.md, with optional files (scripts, references)
    repositories/  installing skills and MCP servers from git repositories: download, copy, install record
    jobs/        scheduled jobs (cron) and their records
    home/        Home, the web app's landing page: sections (the user's instructions), each built by the worker
                 model from its plugins' read-only tools into one format of items, the last results kept in the Store
    doctor/      the daily health check: the day's log records and failed runs grouped by cause, the starting
                 context's size, each against the day before; no model call
    mcp/         MCP servers: settings (Store), connections (hub), their tools as LangChain tools,
                 installing them from a repository (server.yaml; code under ~/.lo9i/mcp/<name>, data under
                 ~/.lo9i/data/<name>), their web pages (pages.py),
                 running a plugin's process (process.py)
    speech/      speech to text (faster-whisper) and spoken replies (Kokoro), set in Settings → Audio; voice audio saved under uploads/audio
    logs/        the daemon's own log: the files it writes (rotated), its records read back as entries with the area
                 they come from (components.py), reading the latest and following a file live (writer.py), the
                 process output read alongside (output.py: output.log or the journal), the level it records at (level.py)
    internet/    the agent's internet access: web search (public engines via ddgs, or the Brave API), page fetching
                 and rendering, URL safety, caching
  daemon/        HTTP API (Unix socket, localhost, HTTPS), device auth, run hub (SSE events), task supervisor, channel routes, scheduler, mail watcher, launchd
  client/        connection.py (connect, auto-starts the daemon), sse.py, errors.py (DaemonUnavailableError),
                 live.py (LiveConversation), files.py (attach by path), recorder.py (microphone)
    daemon_client/ DaemonClient: the conversation as mixins; every other area as a group (`client.channels`, `client.email`, ...);
                 reconnect.py (resumable event streams)
  protocol.py    event JSON shared by daemon and clients
clients/         the apps, each a daemon client
  terminal/      the terminal app (Textual), its own package `assistant_terminal` in the uv workspace; `assistant` opens it
  web/           the web app (SvelteKit); `npm run build` writes it into src/assistant/daemon/webui, served at /app/
```

## Architecture rules

- The daemon is the only process that opens storage or runs the agent. Clients never import `core.agent.AssistantService`; they use `DaemonClient` over HTTP. Conversation calls (`session`, `new_thread`, `send`, `resume`, `events`) sit on the client; every other area is a group named after the part of the daemon it changes (`client.channels.press(name, action)`). New routes go in their area's group, or a new group. Screens receive only the group they use.
- Dependencies point one way: clients -> daemon API -> `core.agent` -> graph -> tools. Core never imports from the daemon or clients.
- Chat channels (Telegram, Slack) are plugins from the extras with a `channel:` section in their server.yaml (`core/mcp/install.py`); the protocol is in `docs/channel-plugins.md`. The daemon runs each enabled one's process (`core/channels/processes.py`) with `LO9I_URL`, `LO9I_CHANNEL` and a token issued for that run. The token reaches only `/channels/<name>/...` (`daemon/auth.py`), where the process holds a stream open (`core/channels/hub.py`), sends what the user does (a message, a button pressed, a command) and tells the apps what to show for it as setup items, which the apps draw with no per-channel code. Everything that is the assistant's runs in the daemon (`core/channels/chat/`): which conversation each message goes to, each run shown as chat messages, approval and question buttons and what pressing them does. It reaches the chat as operations (send, edit, typing, voice) down the stream, each confirmed by the process with its result, so a channel plugin needs no code from lo9i. The daemon also tells the channel its commands (`hello`, then `commands` when an agent plugin comes or goes): /new and each agent's, which hands the channel's conversation to it (`/claude <folder>`, `/claude off`). The plugin declares the protocol version it speaks (`channel: protocol:`); the daemon doesn't run one for another version and the apps say to update it. Core keeps no channel-specific code.
- Messages the agent starts itself (`send_message`) go through `service.outbox`: a channel is registered there while its stream is open. The delivery goes down the stream and waits for the channel to confirm it, so the tool reports real success or failure.
- Every daemon request except `/health` must carry the `X-Lo9i-Client` header (CSRF protection for the network ports). The pages port is the exception: browsers load pages there directly, and the `SameSite=Strict` device cookie it requires is what stops other sites. A client that isn't a browser page (the private watchlist's browser extension, whose requests carry none of the browser's cookies) pairs with `/auth/pair/token`, which returns the device token, and sends it as `Authorization: Bearer`; the pages port takes it like the cookie and never passes it to the page.
- Sign-ins with OAuth (email accounts, remote MCP servers) wait in `core/oauth.py::SignIns` under a one-time state. The browser comes back to the web app's `/app/oauth` page, which posts the state and the code to `/oauth/finish` (`core/agent/sign_ins.py` hands it to the email account or MCP server that started it). That route is open without a paired device (the state is the proof), so the terminal app's sign-in works from a browser on the host that was never paired.
- Mail providers are plugins with an `email:` section in their server.yaml, under the extras' `communications/email/` (`core/integrations/email/providers.py`): presets (servers, OAuth kind, help), no process. An account records the plugin it was connected with and is used only while that plugin is installed and on (`core/integrations/email/plugins.py`); removing the plugin with its data deletes its accounts. A `custom` preset has no servers: the extras' custom-email plugin takes the servers the user types, and installing it takes the accounts that belonged to no plugin (connected by hand before it existed). The allowlist is shared by every account: Settings → General → Email, `/email` in the terminal app.
- Email can sign in with OAuth (Google, Microsoft) through the user's own OAuth app (`core/integrations/email/oauth.py`). The refresh token is the account's secret; access tokens are refreshed when an account is loaded.
- A remote MCP server that answers 401 asks to sign in (`core/mcp/oauth.py`): the SDK's `OAuthClientProvider` discovers its authorization server, registers the assistant there and runs the code flow with PKCE (`core/mcp/sign_in.py`). The registered client, tokens, expiry and authorization server metadata are one secret per server, so a new connection refreshes at the right endpoint. A connection never starts a sign-in: without one, or when the refresh is refused, its status is `needs_sign_in` and it waits for the user to sign in from `/mcp`. A refused refresh (a sign-in that was working) is also recorded as `signed_out` in `core/health.py`: a `signed_out` event alerts every client and it is an alert until the user signs in again or dismisses it. The sign-in is dropped when the server is removed or its URL changes.
- Only the Unix socket is trusted (`daemon/auth.py::trusted`). Every network request, on localhost or HTTPS, needs a paired device: a one-time code from a trusted client, then a token in an `httpOnly` cookie. Never trust 127.0.0.1: port forwarding and proxies make remote traffic arrive from there. Tokens and codes are stored only as hashes (`core/devices.py`). The one other credential is a channel plugin's token: issued in memory each time its process starts, it reaches only `/channels/<name>/...` and is revoked when the process stops.
- Clients learn about background changes from `GET /events` (the `EventBus` in `core/bus.py`), never by polling. Store writes publish automatically (`NotifyingStore`); other changes (skills, job results, runs, bot state) publish explicitly.
- Clients keep running when the daemon is unreachable (`DaemonUnavailableError`). In the terminal app, every handler that calls the daemon is decorated with `@reports_daemon_unavailable` (`clients/terminal/src/assistant_terminal/tui/daemon_errors.py`), and a line above the status says so while its event stream is lost (`ConnectionNote`, from `events(on_open, on_lost)`). In the web app, the event stream's state (`EventHub.getConnection`) shows a banner on every page while it's lost (`ConnectionBanner.svelte`), and every `resource` loads again when it opens again, so pages never show an unreachable daemon as their own error.
- The daemon serves the API and the pages with Hypercorn (`daemon/http_server.py`): over HTTPS a browser and the daemon speak HTTP/2, so a page's requests, event streams and WebSockets share one connection instead of queuing for HTTP/1.1's six per site; plain HTTP on localhost and the Unix socket stays HTTP/1.1, as browsers speak HTTP/2 only over TLS. A stop gives requests in progress `GRACEFUL_SECONDS`; event streams end first (sse_starlette's `AppStatus`).
- Runs outlive the request that started them. Commands are HTTP requests; a run's events stream as Server-Sent Events and can be replayed by event id. A client opening a conversation gets its messages up to its runs in progress and those runs (`GET /conversations/<id>/live`: each run's start in the messages is marked when it takes the conversation's lock, `core/agent/runs.py::_mark_start`), and follows them from their start, so a reply running there shows as if it had been watching; the web app does (`clients/web/src/lib/chat/controller.ts::showHistory`), and the terminal app (`client.conversations.live`, `tui/app.py::_show_history`; in the inbox, which shows the list of conversations, only its runs, at start and on /inbox), and a `run` event for one of them doesn't show it twice.
- Never edit or delete past messages in a checkpoint. History is append-only. The one exception is deleting a whole conversation when the user asks (`delete_conversation`): its checkpoints, list entry, search entries and files go (but files another conversation refers to too, as a message the inbox sent on does; `core/agent/thread_files.py`), while memory learned from it stays.
- When a run ends, its conversation's older checkpoints are pruned (`core/checkpoints.py`): only the latest of each namespace stays, which holds every message and the pending writes an interrupted run resumes from, so no message is lost. The daemon prunes conversations saved before this once at start.
- Messages use LangChain standard content blocks (`output_version="v1"` in `core/llm/`). Code that reads messages uses standard block types, never provider-native ones.
- Checkpoints never hold file contents. Attachments are saved under `settings.uploads_dir` and messages keep a `non_standard` upload reference; `core/attachments.py::hydrate` loads them for each model call, images scaled down to what models look at (`core/images.py`, Pillow; the file on disk stays whole). Tool results can carry files too (images from MCP tools, an email's attachments): their references go in the ToolMessage's `artifact` (`response_format="content_and_artifact"`), which LangChain never sends; `hydrate` adds them to the result, or to a user message after the results for providers that take images only in user messages.
- The system prompt and tool list stay byte-identical within an epoch, so the prompt cache keeps hitting; the one change is a plugin's tools loading (below). The system prompt is built when an epoch starts (`core/conversation/epochs.py`) and stored in graph state. Memory changes take effect in the next epoch.
- Old tool results are sent as stubs once the prompt cache has expired (`core/conversation/trim.py`): at a user message later after the last model call than the provider's prompt cache lasts (`ModelProvider.prompt_cache_minutes` in `core/llm/providers.py`, read with `core/llm/choice.py::prompt_cache_minutes`: 5 minutes unless known to last longer, like OpenAI's own API or DeepSeek, or Anthropic's when its Prompt cache field is set to 1 hour in Settings → Model, which asks for the 1-hour cache, `cache_control.ttl`; a field with `options` is picked from a list in both apps), tool results before the last `TRIM_KEEP_TURNS` user turns are replaced, from then on, by a stub naming the tool, and the files of the user's messages there by a note saying where they're saved. The point is kept in state and only moves forward, so later calls keep hitting the cache. The checkpoint keeps the results whole. A model call refused as too large (HTTP 413 or past the context window, `core/llm/errors.py`) goes to the graph's `shrink` node (`core/conversation/oversized.py`): the epoch is compacted to its last user turn and the trim point moved to the end, current turn included, then the call is made once more; refused again with nothing new since, the run fails with a plain message. A subagent's and a Home section's calls are made again with their tool results and files left out (`oversized.within_size`; a subagent still refused answers that it stopped), and a running summary or a memory digest refused as too large is written in halves (`summary.py`, `digest.py`).
- Prompt texts live in `core/conversation/prompts/`, one `.md` file per prompt, loaded with `prompts.load(name)`. Code doesn't embed prompt text. Tool docstrings and schema field descriptions stay in code.
- The user edits the persona, the operating instructions and the channel hints (`prompts.EDITABLE`) from the web app's Settings → System prompt and the terminal app's `/prompt` (`GET /settings/prompts`, `PUT` and `DELETE /settings/prompts/<name>`, `client.prompts`; `core/conversation/prompt_edits.py`). An edit is a file used instead of the built-in text, read by `prompts.load` each time: the persona's is `SOUL.md`, the others' `~/.lo9i/prompts/<name>.md`; saving the built-in text or resetting deletes it. An edit that can't be read (not UTF-8, no permission) is logged and the built-in text used, and Settings → System prompt (and `/prompt`) shows the problem with Reset, so a broken SOUL.md never stops the assistant. The built-in text an edit was made from is kept beside it (`~/.lo9i/prompts/<name>.base.md`, recorded at start for edits from before or made by hand): when an update changes the built-in text, the section says how (`built_in_changes`, a diff) until the edit is saved again, kept as it is (Keep my edit, `POST /settings/prompts/<name>/kept`) or reset. The other prompts aren't editable: they are templates the code fills in or say how a feature works. Each epoch records a digest of the texts its prompt was built with (`prompt_texts` in graph state); when they change (an edit, or an update to a built-in one), the next user message starts a new epoch with nothing summarized, as with a rename. A `prompts` event tells the clients.
- Per-turn context (date, time, channel) goes in the turn header at the start of each user message, never in the system prompt.
- A new epoch starts only at a user-message boundary, so tool calls and their results are never split. The one exception moves nothing: after a round of tool calls with `offer_plugin`, when the user installed a server, the epoch is reopened at the same point with its tools (`graph.py::_installed_node`), so the agent uses them in that run.
- A new epoch waits only for the running summary of the part it archives (`core/conversation/summary.py`). Memory from that part (episode, profile, facts) is digested after the reply: the part is recorded in the Store (`core/conversation/pending.py`) and the memory writer (`core/conversation/memory_writer.py`, a supervised daemon task) digests parts one at a time, at start and as they're added, so none is lost to a restart.
- Renaming the assistant (`core/identity.py`, `/name` or the `rename_assistant` tool) starts a new epoch at the next user message: the system prompt is rebuilt with the new name and nothing is summarized. Channels hear about it on their stream; the Telegram bot's display name follows the name.
- There is no main conversation: each topic has a conversation of its own. A message written outside one goes to the user's inbox (`core/inbox.py`), which routes it without asking: the graph's first node (`core/conversation/dispatch_nodes.py`) has the worker model pick where it goes (`core/conversation/dispatch.py`: the conversations its words match, then the closest in meaning, then the most recent, each with when it was last written in, numbered in `prompts/dispatch.md`; archived ones never). Closeness in meaning comes from each conversation's title, tags, latest running summary (kept apart from its checkpoint when an epoch starts, `core/conversation/summaries.py`) and first message embedded with the local model, kept with the memories' vectors as kind `conversation` under a key that carries a digest of that text, so a retitled conversation is embedded again (`core/conversation/meanings.py`: `ConversationIndexer`, a supervised daemon task woken by `conversations` events; `SimilarConversations`, which routing goes on without until the index has vectors or when the model fails). A short message that obviously follows up the one before it (that one sent on to a conversation from the same channel, written in there under `FOLLOW_UP_SECONDS` ago, no words matching another conversation's tags) goes where it went without the model (`core/conversation/follow_up.py`); each pick is logged with where the message before went. It goes on in the conversation it continues, or into a new one, which it also does when the model is less sure than the confidence (Settings → Model, `/model`; `core/conversation/dispatch_setting.py`, 0.7 by default), since a wrong new conversation costs least. A quick question one answer settles is answered right in the inbox; a quick exchange lasts `INBOX_TURNS` of the user's messages, and the next one about it moves to a new conversation with what was said (`core/conversation/carried.py`): a turn header note for the model (`prompts/carried_from_inbox.md`), and the lines kept in that message's `additional_kwargs`, which no model call sends, so the apps show the exchange before it, live (`Dispatched.carried`) and in history (a `carried` shown message); the exchange in progress is kept in graph state (`inbox_exchange`). A message sent on is kept in the Store (`core/conversation/dispatched.py`: its content, files and what a voice note said included, and the notes taken when it was written in the inbox, which go with it) and the inbox records it with a line saying where it went (both kept in its history and left out of its model calls, `core/conversation/routed.py`, so a quick answer doesn't read through other topics); a `Dispatched` event tells the client that sent it, which goes there once the run ends (the web app opens it beside the others, the terminal app moves to it, a channel runs it there) and sends it by id (`POST /threads/<id>/dispatched/<dispatch id>`, `send_dispatched`), which adds that conversation's turn header notes. Its line in the inbox carries the message's id: `/move` (the last one) in the web and terminal apps (the web app runs it in a chat on the inbox it never shows, asking its question over Chat), runs the inbox again (`POST /threads/<inbox>/moves`, `move_dispatched`), which picks among the other conversations, asks (moving is the user's correction), and sends it on by the same id; the conversation it left gets a turn header note to leave it out (`core/conversation/moved.py`), since history stays. The assistant moves work that outgrows a quick answer out of the inbox itself, without asking: `move_to_conversation` (`core/tools/side.py`) keeps a brief like a routed message and sends a `Dispatched` event for a new conversation. Unattended runs and conversations of their own go straight to the epoch and the agent. Each conversation has tags the worker model writes with its title (`core/conversation/titles.py`; names and topics, in the user's language and English; a titling that fails is tried again at the conversation's next reply, and the next one that succeeds titles the others waiting, `core/agent/titles.py`), which routing matches a message against (`core/conversation/related.py`; a tag counts when all its words are in the message, and words few conversations' tags use weigh more). The apps open Chat on the list of conversations, newest activity first (the web app's `/conversations`; the terminal app's start and `/inbox`, with `/conversations` to open one); in the terminal app the inbox is a small entry of its own for quick questions and where each message went. The web app never shows the inbox (`clients/web/src/lib/chat/openChats.ts`): Chat opens a new conversation where it would have (a new tab, one gone), whose first message goes on in the conversation it's about as the inbox would pick it, without writing anywhere (`POST /routes`, `core/conversation/first_message.py`; a conversation the user started with /new or + isn't routed); opening the inbox shows the list instead, opening one that was deleted says so, and `/conversations/open` on the inbox gives way to the list (`lib/ui/openConversation.ts::leaveInbox`); its quick buttons write there, showing the reply in their panel. Each client (terminal, browser tab) holds its own conversation: `/new` starts one, `/inbox` goes back to the inbox (terminal app only), `/conversations` opens one. A browser tab holds several side by side (`clients/web/src/lib/chat/openChats.ts`), each under a client id made from the tab's (`partClientId`), so their replies run in parallel: `/new` and the sidebar's + open one beside the others, the sidebar lists them under Chat with any other conversation that has a reply (`GET /runs`) or a coding task running, marking the open ones waiting for an answer (counted on Chat, for when the list is hidden), and closing one tells the daemon (`POST /threads/leave`), which leaves it. A browser tab keeps its open conversations across reloads. A chat channel (Telegram, Slack) has no client to hold one (`core/channels/chat/conversations.py`, `core/agent/channel_threads.py`): a new message goes to the inbox; a reply to a message goes on in that message's conversation, since every message sent in the chat, and the user's own when the plugin sends its id, is kept with its conversation (`core/channels/chat/threads.py`); `/new` sends the next message to a new conversation; and while the conversation the channel last wrote in is handed to a coding agent, messages go on there. Each reply there starts with a short tag of its conversation (`[watchlist] …`: its first tag, or the start of its title; `[inbox]` for a quick answer). Runs are announced with the `client_id` that started them, so every other client on that conversation shows them live.
- The home conversation from before the inbox is kept, once, as an archived conversation (`ThreadsMixin.retire_home`, at daemon start): retitled "Home (before the inbox)", listed and readable, never routed to and never retitled, and what's new in it archived into memory; channels' saved conversations are dropped, so their next message goes to the inbox.
- A conversation no client is on any more is left and archived in the background (`daemon/clients.py`, `core/agent/archive.py`): right away when its client moves to another, after a grace period when its client disconnects. Archiving leaves the part to the memory writer, which adds an episode plus profile and fact updates; covers only what's new since the last archive, and is skipped below `EPISODE_MIN_TURNS`.
- Tools register themselves with `@register("<toolset>")` in a module under `core/tools/`. Enabled toolsets come from settings, never per channel, because a conversation spans channels.
- Every model call is recorded in the token ledger (`core/usage/`: `model_calls` and `token_parts` in SQLite) by a `TokenMeter` set on the model with `llm.metered`, never passed in a call's config (that replaces the run's callbacks and stops streaming). A new place that calls a model attaches a meter with its purpose. The ledger keeps tokens only; `core/usage/prices.py` turns them into money when a report is shown.
- Prefer bash or MCP over a new tool. Every core tool definition is sent on every model call, but those registered in a `group` (email, jobs, skill writing: `register(..., group=)`), which load on demand like a plugin's; plugins' MCP tools only once a conversation loads them.
- New features go in a git repository, not in core: a skill (`<group>/<category>/<name>/SKILL.md`, optional `scripts/`) when it needs only steps or code without secrets, an MCP server (`<group>/<category>/<name>/server.yaml`, format in `core/mcp/install.py`) when it needs secrets, an outside service or a connection that stays open. A chat channel is a plugin with a `channel:` section. Core changes only for the assistant itself (the channel protocol, memory, models, approvals, the apps).
- Only the user installs plugins: installed code runs on this computer. Plugins come from the assistant's extras (`core/repositories/known.py`), built in and the only official repository, and from https repositories the user adds under Repositories in Plugins (web app) or `/plugins` (terminal app), which aren't official (`core/repositories/listed.py`, one Store record). A private one is added with a token that can read it, kept with `core/secret_store.py` and given to git only as an Authorization header for its host, in git's environment (`core/repositories/checkout.py::_auth`); git runs without the system config, so a Mac's Keychain never signs in for it. Plugins lists every repository's plugins, each marked Official or with its repository; the web app shows them at once from each repository's listing kept in the Store with the time it was last checked (`core/repositories/cache.py`, `GET /repositories/plugins?cached=true`), then checks the repositories in the background, and a check that finds something new saves it, announced as `plugins`; a plugin lo9i can't read is left out with its problem (`RepositoryContents.problems`), never the rest of its repository, and `python -m assistant.core.repositories.check <folder>` checks a repository the same way before it's pushed (the extras' pre-commit hook); and installs one from the repository it's listed under; removing a repository leaves what was installed from it, which keeps updating from there; a private one's token stays until the last plugin from it is removed. The update checker reads every listed repository; the agent offers only the extras' plugins. They install from Plugins (web app) or `/plugins` (terminal app), or when the agent offers one: the extras' plugins not installed are listed in the system prompt (`core/repositories/offers.py`, from the listing the update checker keeps), and `offer_plugin` (`core/tools/plugins.py`) pauses the run with a `kind: "plugin"` request that the web and terminal apps show as the install dialog. After an install there, a plugin with a setup (email accounts, a channel's pairing) goes on to it in the same place, and `open_plugin_setup` opens that setup later (`kind: "plugin_setup"`, answered `{"done": true}`). Tokens are typed there and go to the daemon, never through the chat; chat channels can't show it, so there the agent points the user to the app. The tool reads whether the plugin is installed afterwards instead of trusting the answer. Mail providers are the one exception the agent installs itself: their plugins run nothing, so `set_up_email` asks the user which provider their account is with (an `ask_user`-style question), installs that plugin, and opens its accounts (`plugin_setup`); the email tools point to it when no account is connected. When the agent saves or deletes a skill, `approval.ask` asks the user first, so text the agent read can't plant one.
- Every plugin has a category from the fixed list in `core/repositories/categories.py`: a group and a category in it (`communications/email`, `apps/finance`). In the extras a plugin lives in its category's folder (`communications/email/gmail`), which gives its category; a plugin outside those folders declares `category:` in its server.yaml or SKILL.md. A section can require one (a channel is in `communications/chat`, an email provider in `communications/email`). Plugins lists plugins by group; the category only groups them, and what a plugin does comes from its sections. A plugin's own setup (a channel's items, an email plugin's accounts) shows in its details there; group names are only headings, not settings. A plugin that runs only on some systems declares `platforms:` (`linux`, `macos`; `core/repositories/platforms.py`) in its server.yaml or SKILL.md; on any other system it isn't found in the repository, so it's never listed, offered or installed there, and an update that drops this system is refused. A plugin has an icon (`icon:` in its server.yaml or SKILL.md; `core/repositories/icons.py`): a Lucide icon's name, or an SVG file in its folder, checked when the repository is read (only drawing elements, no handlers, no outside links, at most `MAX_SVG_BYTES`) and carried as its text; without one, its category's. The web app shows it in the sidebar's pages, Plugins, Home sections and the notifications of a plugin's work (`PluginIcon.svelte`): a Lucide icon loaded the first time it's shown (`import.meta.glob`, one small file each), an SVG only as an image or, when it draws only in `currentColor`, a mask in the text colour, both as data URLs, so a browser runs nothing in it. The names it checks against are `core/repositories/lucide_icons.json`, which a web test keeps in step with the app's Lucide. An installed server keeps its icon in its record from its install or update; one installed before icons gets it from its installed folder when the daemon starts (`core/mcp/install.py::add_missing_icons`).
- The user pins skills to a conversation (`/pin`, `/unpin`; `core/conversation/pinned.py`, a Store record per conversation). Their instructions go in full in the system prompt of every epoch, so they last the whole conversation, unlike a `use_skill` result that is trimmed and summarized away. Pinning or unpinning starts a new epoch at the next user message with nothing summarized, as with a rename, and that message's turn header says what changed, once.
- A plugin can use a login of lo9i's instead of one of its own: `model_login: copilot` in its server.yaml gives its MCP server the Copilot model provider's GitHub token as `LO9I_COPILOT_GITHUB_TOKEN` (`core/mcp/logins.py`). The hub adds it when it starts the server, it's never saved with the plugin, and a change in `/model` reconnects the servers that use it. The install dialogs say the plugin uses it. In the same way `ssh_agent: true` gives the plugin's processes (its MCP server, page, channel, agent worker) the daemon's `SSH_AUTH_SOCK`, which MCP's default environment leaves out (`core/mcp/ssh_agent.py`), and the install dialogs say so; a daemon started from boot has no agent to pass. A field marked `optional: true` may be left empty.
- A plugin can bring a coding agent (`agent:` in its server.yaml: command, name, worker; `docs/agent-plugins.md`). The plugin brings only the worker, a command that runs one task; everything else is the daemon's (`core/agent_tasks/`): each task is a folder in the plugin's data folder (task.json, pid, progress.log of JSON steps, result.json), the worker is started detached with the plugin's env, keys and login so it outlives a restart, and the daemon follows its files with watchfiles. While an agent plugin is installed the assistant gets the task tools (`start_task`, `task_status`, `list_tasks`, `stop_task`, `core/agent_tasks/tools.py`); they come with the MCP tools through `core/plugin_tools.py`, frozen per epoch, and starting or stopping a task asks the user unless the plugin is trusted. Where the user watches, a task goes to the agent as a conversation, so its steps are that conversation's, kept in history. In a conversation, `start_task` hands that conversation to the agent and queues the task (`core/conversation/queued.py`), which the daemon sends as a run of its own once the reply ends (`daemon/queued.py`), so every app shows it. The task is the assistant's words, not the user's: its message keeps the agent's name (`core/conversation/briefs.py`), its run is announced with it (`brief`, as is a task moved out of the inbox, in its `Dispatched` event), and history shows it as a `brief`, which the apps show collapsed as "Task for <agent>" and never pin as the user's message. In the inbox it moves the task to a new conversation without asking (`moved_out_of_inbox`, `core/tools/side.py`): the task is kept like a routed message with the agent's command and folder, and `send_dispatched` hands the new conversation to the agent before the task goes to it (to the assistant instead when the folder went away). The inbox itself can't be handed over; `/claude` there hands a new conversation. In a scheduled run the task runs in the background. While `task_status` waits for a task, its steps show inside that call (`steps.py::within_call`) and are kept with its result as a delegate call's are (`core/subagent_steps.py`), so history shows them there again; while any task runs, every step is an `agent_task_progress` event and `GET /agent-tasks/running` lists the running tasks with the conversation that started each and their latest steps, which the web app shows above the composer and the terminal app under its title (`core/agent/tasks.py`). The apps add its command: `/claude <folder>` hands the conversation over (`core/conversation/handoffs.py`, a Store record per conversation), `/claude` alone opens a folder picker (the workspace `~/.lo9i/claude-workspace`, folders used before, browsing from the home folder, hidden folders only after Show hidden; `core/conversation/agent_folders.py`), `/claude off` takes it back. While it's handed over, each message runs as a task continuing the conversation's session in that folder (`AgentTasks.converse`; no model, no approval: switching is the user's consent) as a cancellable run, and the message and reply are appended to the conversation; while it works, what the user writes there goes to the task between its steps (`message_agent`; the task's `inbox/`, `docs/agent-plugins.md`), with the files attached saved as uploads and given to it as their paths (the daemon keeps what the user wrote and the files' references with its step, `core/agent_tasks/sent.py`, so the apps show them as files and the conversation keeps them as any message's: the Files list, deleting it), and the API's `interrupt_agent` stops its step in progress, leaving it waiting for the next message (no app offers it), and those messages show among its steps (`UserSaid`), live and in history; once it is done with the job (its run ends with a reply or an error, and no message waits in the conversation's queue) an `agent_finished` event tells the apps, and the web app plays a sound and shows a pop-up, each turned on or off per browser in Settings → General (`lib/agentDone.ts`); when it comes back, the next message's turn header tells the assistant the replies were the agent's, once. Files sent to an agent are saved and kept in the conversation like any attachment; the agent gets their full paths after the message and reads them from disk (`core/agent/messaging.py::_to_agent`). Its steps become the run's events (`core/agent_tasks/steps.py`): `TextDelta` for what it says and for its thinking, which shows as a message like its reply, and a `ToolStarted`/`ToolFinished` per call, so the work reads like a reply, its words streaming as they're written (`text_delta`, `thinking_delta`); a note goes inside a call named after the agent. The steps are kept with the reply in its message's `response_metadata`, which no model call sends, so history shows them again (`core/conversation/display.py`), its own subagents' tool calls inside the call that started them, as live. A plugin written for the old format (an MCP `converse` tool) isn't offered until it's updated.
- MCP servers are added from the app (`/mcp`), never by the agent. Their tools are named `mcp__<server>__<tool>`; the user picks which ones the agent gets. Their definitions are most of a request, so they load on demand (`core/plugin_loading.py`): an epoch offers the core tools, the task tools and `load_tools`, and the system prompt lists each server with its tools' names (Plugin tools), and each group of the assistant's own tools that loads the same way (`core/tools/registry.py::tool_groups`: email, jobs, skill-writing; `core/plugin_tools.py`), which run as any core tool once called. A round of tool calls loads a server's tools for the rest of the epoch when it calls `load_tools` for it, uses a skill that comes with it (`use_skill`), installs it from `offer_plugin`, or calls one of its tools anyway; an epoch starts with its pinned skills' servers loaded, and a scheduled run's with those its job's task names (a skill that comes with one, an `mcp__<server>__` tool, a group's tool by its name; `plugin_loading.named`). Graph state keeps the loaded servers (`loaded_plugins`), their definitions (`mcp_tools`) and the list the prompt shows (`plugin_tools`), so they survive turns and restarts; loading changes the tool list (one cache miss), a new epoch at the same point keeps them, and one that summarizes keeps those the turns it keeps called. When the servers' tools change, the next user message starts a new epoch with nothing summarized, as with a rename; a server installed from `offer_plugin` brings its tools right after that call instead (the tool waits up to `_START_SECONDS` for it to connect, `McpHub.started`). Calls look the tool up live in `McpHub`, so a tool turned off stops working at once, and one whose server isn't loaded still runs. Subagents get the read-only tools of the plugins the conversation loaded, and Home's sections their plugins'. Local servers run on demand (`core/mcp/on_demand.py`): their tools are kept from their last connection (`core/mcp/tool_cache.py`), the first call starts them and they stop after `IDLE_SECONDS` without calls; an update forgets the tools, so the server starts at once to learn them again. Remote servers stay connected. On an untrusted server, tools not marked read-only go through `approval.ask`; after a dropped connection only read-only calls are retried.
- Failures of MCP servers and skills are counted in a row per server and per skill (`core/health.py`, in the Store): failed connection attempts and failed or erroring MCP calls (`core/mcp/connection.py`), and skill scripts that exit non-zero or time out, found by their folder in a bash command (`core/skills/tracker.py`, a run callback reading bash's exit-code artifact). Only a working call or script clears the count. At `FAILING_AFTER` in a row a `failing` event alerts every client, and it becomes an alert (`core/agent/alerts.py`, the web app's Alerts page and sidebar bell) that stays until the user dismisses it or it works again; a turned-off server or deleted skill has none. The /mcp and /skills screens show the count and the last failure. A skill whose SKILL.md header is invalid or whose instructions use files it doesn't have lists its `problems`; such a skill isn't installed, updated or saved.
- An MCP server installed from a repository can come with a web page (`page:` in its server.yaml). `core/mcp/pages.py` runs it on a Unix socket in the server's data folder; `daemon/pages.py` serves it to paired devices on the daemon's port plus one, a separate origin so its scripts can't call the API, removing the device cookie and refusing its cookies. A request's answer streams through as the page writes it (Server-Sent Events, a long download), the page having `FIRST_BYTE_SECONDS` to start answering and no limit after; what goes both ways (a terminal) is a WebSocket to the same path, passed through both ways with no time limit (`daemon/page_sockets.py`): the same paired device, only from the pages' own origins (a browser sends its cookie with a WebSocket from any site) or with no Origin and a bearer token, closed when the device is revoked (`DeviceStreams`, shared with the API). The web app shows it in an iframe from the sidebar, and tells it the app's theme, since it can't read the app's: `?theme=light|dark` on its first address and a `{"type": "lo9i:theme", "theme"}` message to the frame when it changes (`clients/web/src/routes/pages/[name]`); the extras' pages keep it for their next pages and have both themes.
- Actions that need approval go through `core/tools/approval.py::ask`: bash commands matching `bash_guard.py`, email to recipients outside the allowlist. In unattended runs (channel `worker`, scheduled jobs) the scheduler forwards them to the channels registered in `service.approvals` (`core/approvals.py`; every connected channel, with `ja:`/`jr:` buttons) and waits up to `JOB_APPROVAL_MINUTES`, which doesn't count toward the run's time limit. With no channel connected, or no answer in time, they are denied and the job is recorded as needing attention. Runs in progress are kept in the Store (`core/jobs/active.py`): after a restart, a run that was waiting for approval asks again once a channel connects, and one stopped anywhere else is recorded as failed.
- The agent asks the user to pick among options with `ask_user` (`core/tools/questions.py`). It pauses the run like an approval: an `ApprovalRequired` whose request has `kind: "question"`, answered with `{"choices": [...]}` (`null` when skipped). Every client shows it: checkboxes in the web app, a selection list in the terminal app, buttons in Telegram and Slack (the picks travel in the button data, `core/channels/chat/questions.py`). Unattended runs aren't asked. A new message in a conversation whose run waits for an answer declines what it waits for (an approval rejected, a question skipped, a plugin not installed; `events.declined`): the tool calls finish with that, the run stopping before the model (`interrupt_before`), and the model then reads them with the new message and answers it (`core/agent/runs.py::_declining`).
- A reply that ends with a question with a few clear answers (yes or no, two to four short options) lists them in a marker at its end, `<!-- choices: Push | Commit only | Cancel -->` (`prompts/operating.md`), with no pause and no tool. History keeps it as the model wrote it. The web app shows its choices as buttons under the last reply while nothing runs; pressing one sends it as the user's message, and any message after it takes them away (`clients/web/src/lib/chat/choices.ts`). Everywhere else the marker is taken out (`core/conversation/choices.py`: `without_markers`, and `Streamed` for a view that only appends): the chat channels' replies, the terminal app's, the job replies and notifications (`last_reply`), the exchange the inbox carries on. Holding back an open comment at the end keeps a marker still streaming from flashing.
- The agent hands self-contained tasks to a subagent with `delegate` (`core/tools/delegate.py`, `core/subagent.py`): a small graph on the worker model with its own prompt and no epoch, memory or turn header, run inside the tool call, whose final reply is the tool result. It gets only tools registered with `subagents=True` (they read or work on this computer; nothing that talks to the user, sends, schedules or saves) and the read-only MCP tools of the plugins the conversation loaded (`loaded_plugins`), and its last step's tool calls don't run (`SUBAGENT_MAX_STEPS`). Every tool call runs as a task of its own (`graph.each_tool_call`), so a subagent's checkpoint lives under its call's namespace in the conversation's thread: an approval inside it pauses the run, and the answer resumes it where it stopped, and the Files list and deleting the conversation read the files its tools brought there (`core/agent/thread_files.py`, `checkpoints.subgraph_namespaces`; the Files list from an index of each conversation's files written when its runs end, `core/conversation/file_index.py`). Its tool calls stream as `ToolStarted`/`ToolFinished` with `within` set to the delegate call's id, which the apps show inside that call; they're kept with the call's result, in its `response_metadata`, which no model call sends (`core/subagent_steps.py`, each output cut at `_MAX_OUTPUT`), so history shows them inside the call again, with its task and answer (`core/conversation/display.py`). History sends every tool call, a delegate or task_status call's answer and steps and a handed-off agent's calls included, as its start, and the apps load one whole when it's opened (`GET /conversations/<id>/tool-calls/<call id>`, a step by its place: `.../steps/<n>`; a handed-off agent's call is named after its reply and its place, `agent~<message id>~<n>`). Scheduled jobs don't delegate.
- Messages the assistant sends on a channel from outside that channel's conversation (`send_message` from a job or another chat, new-mail alerts) are recorded with `core/conversation/sent.py` and go into the turn header of the user's next message on that channel, once.
- The web app opens on Home (`core/home/`, `GET /home`): sections the user edits (title, what to show, the plugins it reads; `PUT /home/sections`, built-in ones from `prompts/home_<id>.md` until then), each built by the worker model with only the read-only tools of its plugins (`core/home/builder.py`: a small graph gathers, then `build_structured` writes `SectionContent`, items with a day and time, which pydantic validates). Plugins aren't changed for it. Each section's last result is a Store record, saved as it's built (a `home` event), so the page shows the last results at once and updates itself; one that fails keeps its items and says why, one whose plugins aren't installed says so without a model call. Showing Home asks for a refresh (`POST /home/refresh`), which runs in the background unless one runs or the last ended under `FRESH_MINUTES` ago that same day; Refresh forces it, and saving sections builds the new and changed ones. The daemon keeps it current on its own (`core/home/schedule.py`, a supervised task ticking on the wall clock): on the first tick of the user's day, and every `WATCHED_MINUTES` while a client shows it (the web app's Home tab says so while it's visible, and the terminal app's `/home` while it's open, which shows the sections with Refresh and editing as the web app's page does, `PUT`/`DELETE /home/watch`; a client whose event stream closes is forgotten, `ClientRegistry`'s `gone`).
- Job results and background work that ended go to a notifications feed apart from any conversation (`core/notifications.py`, a Store record each, the latest 200): the scheduler adds each job run's result (`daemon/scheduler.py`; not runs skipped), naming its job and run, a run that started more than `_LATE` after it was due saying how late, and a run missed (due while the daemon wasn't running, past `JOBS_GRACE_HOURS`) saying so, `BackgroundEnds` each end, named after the conversation it was started in and linking to it. The web app's Notifications page and the terminal app's `/notifications` list them, newest first, open the conversation or, for a job's run, the job (the Jobs page, `/jobs`) with that run's whole reply (`GET /jobs/<name>/reply?at=`, read from the run's conversation; its record keeps only the end), dismiss or clear them (`GET /notifications`, `POST /notifications/read`, `DELETE /notifications[/<id>]`); the sidebar counts the unread ones. Toasts and chat channel messages still come as before.
- The doctor checks the daemon's health once a day (`core/doctor/`), so problems show without anyone reading the logs; it never calls a model. A check of a day reads its records at WARNING or above in `errors.log` and `daemon.log` across their rotated parts, each record once, and groups them by cause: the last exception line and the last frame in lo9i's code (or the first line and the logger), with numbers and ids left out, so the same cause keeps its id across days and versions (`log_causes.py`, `causes.py`). It reads the checkpoints of the conversations written in that day and of the scheduled jobs' runs started then (from their run records; a job's run links to it on the Jobs page) (`conversation_causes.py`): each turn counts once, as the run's failure (a run that fails marks it in its conversation, `core/conversation/failed.py`, which no model call sends and history shows as its error; or the error the checkpoint keeps), tool calls left without results (`unanswered.unanswered`), or no reply (a run stopped before it answered); a turn a run is still on, or waiting for an answer, doesn't. It measures the context a new conversation starts with, the system prompt part by part (`prompt.prompt_parts`, the parts an epoch's prompt is joined from) and the tool definitions, at the daemon's token estimate (`usage/tokens.py::estimate_text`), against the model's context window, as the context bar measures a conversation (`core/llm/windows.py`: Anthropic's and Copilot's model lists say it, learned once per model and kept in the Store; `EPOCH_MAX_TOKENS` where the provider doesn't say; compaction still starts at `EPOCH_MAX_TOKENS`) (`context.py`). It compares with the report of the latest day checked before (`changes.py`): new causes, causes happening more than `GROWING_TIMES` as often, causes gone, how each part of the context grew; with no earlier report nothing is new. Causes the user marked as known noise are left out (`PUT`/`DELETE /doctor/known/<id>`). Each report is kept, one per day for `KEPT_DAYS` (`records.py`, a `doctor` event), and goes to the notifications feed (kind `doctor`, which the apps open on the health check); its new or growing causes and a starting context past `ALERT_SHARE` (30%) of the window are alerts (area `doctor` in `/alerts`, named after the cause, saying which parts grew most) until dismissed. The daemon checks each day once it ended (`schedule.py`, a supervised task ticking on the wall clock, which checks each day since the last one it has a whole-day report of, up to the day before and at most `KEPT_DAYS` back, oldest first); the apps check today so far in the background (`POST /doctor/check`, `GET /doctor`): the web app's Settings → Health page and the terminal app's `/doctor`, with Check now and marking a cause as known.
- Background work that ends after its call returned is told to the conversation that started it (`core/background.py`, `docs/background-work.md`): a note in the turn header of the user's next message there (`core/conversation/ended.py`), an entry in the notifications feed, a `background_ended` event every app shows as a toast (the web app's opens the conversation), and a message on the chat channel it was started from, kept with that conversation so replying to it goes on there (as `send_message`'s are: `Outbox.send` returns the ids the channel confirmed, `core/channels/chat/threads.py::record_own`). When the work failed, or its end asks for it (`follow_up` in an MCP server's `work_finished`), the assistant follows up unasked: a follow-up is queued in that conversation (`core/conversation/queued.py`) and the daemon runs it once nothing runs there (`daemon/queued.py`, woken by a `queued_messages` event), a message with only the note and no text of the user's (`core/agent/follow_ups.py`), which routing skips and the apps show as the notice (a `notice` shown message in history; live, the `run` event carries it as `notice`); not in a conversation handed to an agent or waiting for an answer. Tasks started with `start_task` are recorded with their conversation (`core/agent_tasks/reports.py`) and followed to their end by `TaskEnds` (`core/agent_tasks/ends.py`, a supervised daemon task), across restarts; when the assistant reads the end first (`task_status`, `stop_task`) nothing is told, and an end is never told while `task_status` is reading the task. An MCP server reports its own: every call carries `_meta["lo9i/origin"]`, which the server sends back in `notifications/lo9i/work_finished` on its connection (`core/mcp/background.py`, the client extension `lo9i/background`); between `notifications/lo9i/work_started` and the end, a server on demand isn't stopped as idle.
- The mail watcher (`daemon/mail_watcher.py`) keeps one IMAP IDLE connection open while new-mail alerts or a mail job want it, and hands new messages to `Scheduler.run_for_mail`. The last UID seen is saved before delivery, so restarts never repeat or flood.
- Jobs repeat on a cron `schedule`, run once `at` a local time (then turn themselves off), or run `on_new_mail`. Scheduled jobs run in their own conversation (`job:<name>:<time>`), are never archived as episodes, and only run while the daemon runs. `/startup` makes the daemon run from boot: LaunchDaemons on macOS (with Ollama), a systemd user service on Linux (`daemon/startup.py` picks the backend).

## Code rules

- No quick workarounds or shortcuts. Fix the cause with the right design, even when a stopgap (polling, sleeps, retries, special cases, silenced errors) would be faster. If a proper fix isn't possible yet, say so and add it to `BACKLOG.md` instead of shipping the stopgap.
- Private functions, methods and attributes start with `_`. Anything without `_` is public API of its module.
- Keep functions small and single-purpose. If a function needs a comment to separate its steps, split it into functions. Aim for under ~20 lines.
- Apply SOLID:
  - Single responsibility: one reason to change per class and module.
  - Open/closed: add behavior with new classes or functions (new tool, new channel) instead of editing unrelated code.
  - Liskov: subclasses and protocol implementations must be usable wherever the base is expected.
  - Interface segregation: small protocols with only the methods callers need.
  - Dependency inversion: depend on abstractions and pass dependencies in (constructor or arguments). No hidden globals beyond `settings`.
- Large classes are a facade composing mixins, one file per concern (see `core/agent/`). Shared attributes are declared on a base class. New behavior goes in a new or matching mixin, never in the facade.
- Type hints on all public signatures.
- Async all the way in core. No blocking I/O in async code.
- Match the style of surrounding code. Comments explain why, not what.

## Tooling

- Python 3.12, managed with `uv` as a workspace: the root package and `clients/terminal`. Add dependencies with `uv add` (`uv add --package assistant-terminal` for the terminal app), never pip.
- Before every commit run `uv run ruff format`, `uv run ruff check` and `uv run pyright`, and `npm run format` in `clients/web` (Prettier); all must pass. Fix findings instead of disabling rules. A `# pyright: ignore` is only for a verified defect in a library's types, with a comment saying which.
- Tests live in `tests/`, one folder per area (core, internet, daemon, client, terminal); the channel plugins' tests live with them in the extras. Run `uv run pytest` before every commit; it is offline and uses temporary data paths, never `~/.lo9i`. `uv run pytest -m live` runs the tests that need the network or large downloads (search engines, page rendering, the speech model).
- New behavior comes with tests. Use the fixtures in `tests/conftest.py`: `script` (fake model replies), `digests` (fake epoch digests), `service`, and `tests/terminal/conftest.py` for the terminal app.
- Run locally: `scripts/run.sh` (starts Ollama when `.env` points at it, then the terminal app, which starts the daemon). Nothing runs in Docker. `assistant daemon` runs the daemon in the foreground. The daemon writes its log itself, however it was started (`core/logs/`): `~/.lo9i/logs/daemon.log` and `errors.log`, rotated, shown in the web app's Settings → Logs and `/logs`, which follow them live over Server-Sent Events; in a terminal its records show there too. What isn't a record (a crash before logging starts) goes to `~/.lo9i/logs/output.log` when the terminal app or launchd started it (past `daemon/output.py::LIMIT` at start, it's kept as `output.log.1` and the daemon writes to a new one), to the journal under systemd; the Logs page shows it as `output` and follows it by watching the file (watchfiles) or with `journalctl --follow` (`core/logs/output.py`). A LaunchDaemon installed before the logs moved still sends it to `~/.lo9i/daemon.log`, so the daemon points its own stdout and stderr at `output.log` at start (`daemon/launchd.py::move_legacy_output`). The level it records at is a setting (Settings → Logs, `/logs`; `core/logs/level.py`) applied without a restart: to the assistant's own loggers, while libraries stay at INFO. A plugin's process (a channel, a page) logs its output under a logger named after it (`assistant.core.channels.<name>`, `assistant.core.mcp.pages.<name>`), so channels are a component of their own. `scripts/restart.sh` (`assistant daemon restart`, POST `/system/restart`, `daemon/shutdown.py`) restarts the running daemon so code changes take effect, once no run is in progress. Restart it that way, never by stopping its process: a conversation handed to an agent (/claude) runs inside the daemon, so stopping it stops that agent before it replies. The apps restart or stop it too (Settings → System, `/host`; POST `/system/stop`), also once no run is in progress. A restart starts the process again in place, however it was started; stopping depends on what started it (`daemon/managers.py`): one started by hand exits, systemd is asked to stop its service, and launchd leaves it stopped after a clean exit (its plist's `KeepAlive` is `SuccessfulExit: false`; a plist from before restarts it whatever its exit, so stopping is refused until start at boot is turned off and on). One started by hand while start at boot is on runs beside the service, which keeps trying to start and would take over once it exits: on Linux stopping stops the service's tries first, on macOS it's refused (stopping launchd's tries needs an administrator). While a restart or stop waits for runs it's pending (`GET /system/ending`), whoever asked: the web app's Host card and `/host` show it with what it waits for (runs, an update being installed: `PendingEnding`) and Cancel, which takes it back (`DELETE /system/ending`, an `ending` event with `taken_back`; not the restart an installed update needs, `can_take_back`), and Now, which cancels the runs so it goes ahead (`POST /system/ending/now`), so a run that never ends can't hold it forever. A daemon that finds another one running exits with `EX_TEMPFAIL`, so the service manager tries again. A LaunchDaemon installed by an older version says how it differs (`StartupStatus.outdated`: where the output goes, whether it can be stopped, which Python it starts), and the Startup card and `/startup` offer Install again (`POST /system/startup/reinstall`, one password dialog): beside a daemon started by hand it installs as turning it on does; under the daemon it runs, the new plist goes in place and is loaded once that daemon exits (`launchd.install_for_relaunch`, run in a session of its own so launchd doesn't stop it with the daemon), which it does once no run is in progress (`Shutdown.relaunch`, `Ending.RELAUNCH`: a clean exit instead of a restart in place, which can't be taken back, `needed_by`). The Host card and `/host` say why Stop can't work before it's pressed (`HostStatus.stop_refusal`). Every restart or stop asked for, from any app or by an update, is announced as an `ending` event with the runs it waits for, so every app says so (the web app's `ConnectionBanner`, the terminal app's `show_ending`), not only the one that asked; when the web app's event stream opens again it checks its build's `version.json` (`updated.check()` from `$app/state`, once per reconnection, never polled) and offers Reload when a new web build replaced it.
- Updating from the apps (Settings → System's Host card, `/host`; `daemon/updates.py`, `GET /system/update`, `POST /system/update/check`, `POST /system/update`): the version is the commit lo9i runs. A clone checks its upstream branch (`git fetch`) and lists the commits it doesn't have; an update waits for the runs in progress to end, then holds new ones off until the restart (`hold_runs`: refused with a message to send them again once it's back, let through again if it fails), so no run uses the old code against the new files; it then fast-forwards to it, runs `uv sync --frozen --inexact`, builds the web app when npm is there, then restarts (`Shutdown`, once no run is in progress), each step an `update` event. One that fails after the fast-forward goes back to the commit it came from (its tree was clean, so `git reset --hard`) and runs the steps that had run again there; when that fails too, its error, shown in the Host card and `/host`, says a restart would run a version that isn't fully installed. An update the daemon ended in the middle of all the same (its task cancelled outright, a crash) leaves a mark in the clone's git folder with the commit it came from; the next start goes back to it, runs every step again there and restarts (`Updates.recover`). A clone with changes not committed or commits not pushed is left as it is, with why. A copy `scripts/deploy.sh` made has no `.git`: it carries the commit it came from in `.lo9i-version` and is updated by deploying again.
- Install: `install.sh` at the repo root, piped from curl (clones into `~/lo9i-assistant`) or run in a checkout. It installs uv and the dependencies, asks for the provider and key the first time and writes `.env` on that computer, and on Linux runs the daemon as the same systemd user service `/startup` installs. `scripts/deploy.sh user@host` copies this working tree to a host and runs install.sh there; it never copies `.env`.
- Data lives in `~/.lo9i`: `lo9i.db` (SQLite), `uploads/`, `models/`, `workspace/` (bash), `browsers/` (headless Chromium for page rendering), `SOUL.md` and `prompts/` (the user's edits of the system prompt texts), `daemon.sock`, `logs/` (the daemon's log), `cli_history` (the terminal app's input history, kept by the client).
- The model (provider, its fields, main and worker model) is set from the app with `/model` or Settings → Model, saved in the Store and overriding `.env` (`core/llm/choice.py`). Providers are listed in `core/llm/providers.py`: Anthropic, Copilot and OpenAI-compatible have their own builders, every other one goes through LangChain's `init_chat_model` with the field values as keyword arguments. A provider's package is installed with uv when it's first chosen, or at start if it went missing (`core/llm/packages.py`); `install.sh` syncs with `--inexact` so deploys keep them. Saving asks each model to answer once; the service then rebuilds its graph, digester and titler (`core/agent/model.py`), so the change applies without a restart. Model builders take a `ModelChoice`, never read the provider from `settings`. The Copilot and OpenAI-compatible models connect with TCP keepalive (`core/llm/connections.py`): a computer that sleeps counts timeouts only while awake, so a call on a connection that died in the sleep would otherwise wait out its 600s read timeout in time awake, hours on a laptop.
- Telegram and Slack are installed as plugins (`/plugins`, or Plugins in the web app), their tokens entered as the plugin's fields; their setup (pairing, status) shows in the plugin's details in Plugins. Telegram's paired accounts live in the plugin's data folder. Slack uses Socket Mode, so it needs no public URL.
- A plugin's keys are encrypted with `core/secret_store.py` (`core/mcp/keys.py`): the values its fields were given, and every env and header value of an MCP server added by hand. Its Store record keeps their names with empty values, so a server is saved with `keys.save`, never `servers.save`, and whatever starts or connects it (the hub, pages, channel processes, updates) fills them in with `keys.fill`. Removing a plugin keeps its keys, and a private repository's token when nothing else needs it, and returns them (`KeptKeys`): the apps ask Keep or Delete (`POST /plugins/keys/forget`), and list what's kept later with Delete (`GET /plugins/keys`: Settings → System's Kept keys, the terminal app's `/keys`), each plugin's keys while it isn't installed again and each private repository's token nothing needs any more. Kept keys fill the fields left empty when it's installed again. A server added by hand has nothing to install again, so its keys go with it. Keys saved in plain records before are moved out when the daemon starts.
- Services the user can connect more than once (email now) are accounts (`core/accounts.py`): a Store record per account with its settings, one default per kind. Their passwords and tokens, and the model's API key set in the app (`core/llm/choice.py`), go only through `core/secret_store.py`, encrypted with the key file at `SECRETS_KEY_PATH` (`~/.lo9i/keys/secrets.key`, outside the database), never in a plain Store record. Tools that act on an account take an `account` argument (label, address or id; empty for the default), and the system prompt lists the accounts at the start of each epoch, so the tool list never changes.
- Web UI conventions, including the default page layout, are in `clients/web/WEB.md`. Follow them for new pages.
- Never require the user to run shell commands for app features. Setup flows go through the daemon API so every client, including the web UI, can offer them.
